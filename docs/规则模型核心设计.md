# Mosika 规则模型核心设计

> 适用模块：`mosika-core`
>
> 内容依据：`mosika-core` 当前源码与核心测试

本文描述 `mosika-core` 内核的设计构思、语义边界和运行机制：DSL 与 JavaScript 两层语言如何分工、`RuleNode` 递归树如何统一表达逻辑与流程、`EvalResult.matched` 与 `EvalResult.result` 为何必须分离、`$`/`$$`/`$args`/UDF 如何构成完整表达式执行环境、模板参数化如何让同一 `ruleId` 在一棵树中按节点独立实例化、`RuleSuite` 如何把规则与 UDF 装配成可执行套件。

本文只讨论内核，不讨论 UI AST、页面布局、Web API、持久化和产品层 Flow。凡涉及可视化编排（UI 树、节点编辑、画布）的内容，见兄弟文档[《规则编排交互设计》](./规则编排交互设计.md)；凡涉及部署、UDF 定义/Spring 装配/运维操作的内容，见兄弟文档[《运维与开发》](./运维与开发.md)。

## 1. 设计理念

### 1.1 一句话架构

Mosika Core 是一个以 `RuleNode` 递归树为执行模型、以规则 ID DSL 为结构语言、以 JavaScript 为业务表达式语言、以 UDF 为扩展机制、以 `RuleSuite` 为可执行装配单元的通用规则引擎。

它有意把能力拆成两个层次，而不是塞进一种语言：

```text
结构层：规则 ID DSL
    负责 与、或、非、命中数、条件、串行、并行、循环及其作用域

计算层：JavaScript 表达式
    负责读取业务对象、调用 Java/UDF、计算和返回业务值
```

结构层决定“执行哪些规则以及如何组合”，计算层决定“每条原子规则具体做什么”。若直接在流程 DSL 中嵌入完整业务 JavaScript，会带来三个问题：结构解析器必须理解 JavaScript 的字符串、正则、对象字面量和运算符；UI、持久化和规则复用无法稳定引用原子规则；执行详情难以用业务规则 ID 归档和解释。当前设计让 DSL 只解析有限、稳定的组合语法，把复杂计算交给成熟的 JavaScript 引擎。

### 1.2 AST（其 JSON）是唯一事实来源

编辑、持久化、编译、执行、追踪和回放共用同一份 AST，模型永不从执行树反向重建。在内核内，这意味着：`RuleNode` 及其递归组合是执行语义的唯一来源，语义由节点类型和父子关系承载，而不是从文本位置、坐标或边方向推断。产品层的 UI AST 是编辑侧的唯一事实来源，一路向下单向编译为 `RuleNode`（见[《规则编排交互设计》](./规则编排交互设计.md)），不做反向恢复。

### 1.3 树是执行语义，不是展示结果

Mosika 使用递归树表达控制作用域，不使用通用 DAG：

```text
S(
  P(a, b),
  P(c, d)
)
```

该结构明确表示：先并行执行 `a、b` 并等待完成，再并行执行 `c、d`。并行子树的结束就是局部作用域的自然汇合，不需要多入边、隐式汇合点或额外图算法。

### 1.4 匹配状态与业务结果分离（结果契约）

任意节点都可能同时具备两个维度：它作为条件时是否命中；它实际产生了什么业务值。因此 `EvalResult` 同时保存：

```text
matched  逻辑或控制状态
result   业务返回值
```

二者不能互相替代，责任必须分开：`matched` 表达匹配/控制状态，`result` 只承载节点有意义的业务返回。逻辑节点主要解释 `matched`；条件分支和动作可能传递 `result`；串并行结构只表示执行完成。不要把诊断/状态塞进 `result`；不要为 `EvalResult`/`RuleResult`/`NodeResult` 增加字段或改动序列化而不与维护者对齐。

### 1.5 规则作者处于可信执行边界

规则表达式不是面向不可信用户的安全模板，而是可执行 JavaScript。设计上允许：访问 Java 对象属性和方法、使用 `Java.type(...)`、传递和返回 `BigDecimal` 等 Java 类型、调用 Java UDF 和 JavaScript UDF、通过 `$$` 读写本次规则上下文。因此 Rhino 的 Java 互操作能力是产品能力，不是默认需要消除的暴露面。若调用方需要不可信脚本隔离，应在内核外另建授权与运行边界，不能通过缩减表达式语义实现。

### 1.6 编译配置与单次执行状态分离

规则和 UDF 在 `RuleSuite` 构造阶段完成装配；一次顶层求值创建独立的 `RuleVisitor`，并在一个 Rhino `Context` 中执行当前线程上的多段规则脚本。每段脚本仍创建独立 JavaScript 子作用域；并行分支在工作线程中分别进入自己的 `Context`。三类生命周期为：

```text
套件生命周期：RuleSuite / RuleEngine / 编译 Script / UdfContainer / UDF 共享作用域
顶层求值生命周期：RuleVisitor / RuleContext / EvalNode 详情树 / 当前线程 Rhino Context
脚本求值生命周期：独立 Scriptable / $ / $$ / $args
```

### 1.7 总体分层

```text
RuleLoader
  ├─ RuleDefinition[]
  └─ UdfDefinition[]
          │
          ▼
RuleSuite 构建与编译
  ├─ RuleEngine
  │    ├─ JavaScript Script 缓存
  │    ├─ 唯一规则注册表
  │    └─ UDF 定义树
  └─ NodeBuilder
       ├─ 套件专属 NodeGenerator
       └─ 命名复合 RuleNode 缓存
          │
          ▼
evalRule / evalExpr
          │
          ▼
RuleVisitor + RuleNode 递归执行
          │
          ├─ ExprNode ──> RuleEngine ──> Rhino
          ├─ 逻辑节点 ──> 解释 matched 并短路
          ├─ 流程节点 ──> 控制执行顺序或并发
          └─ EvalNode ──> 构建执行详情树
          │
          ▼
NodeResult
```

## 2. DSL 语法与运算符

### 2.1 外层：规则 ID DSL

ANTLR 语法位于 [`Rule.g4`](../mosika-core/src/main/antlr4/Rule.g4)。DSL 的原子项是规则 ID，组合能力包括：

| 语法 | 节点 | 含义 |
| --- | --- | --- |
| `!a` | `NotNode` | 对规则命中状态取反 |
| `a&&b` | `AndNode` | 逻辑与，遇到未命中即短路 |
| `a\|\|b` | `OrNode` | 逻辑或，遇到命中即短路 |
| `all(a,b,c)` | `AllNode` | 全部子规则命中，继承 `AndNode` |
| `any(a,b,c)` | `AnyNode` | 任一子规则命中，继承 `OrNode` |
| `a?b:c` | `CaseNode` | 根据 `a` 选择一个执行分支 |
| `a?b` | `CaseNode` | 仅有命中分支的条件执行 |
| `a->b` | `SerNode` | 串行执行结构 |
| `a=>b` | `ParNode` | 并行执行结构 |
| `some(2,_,a,b,c)` | `SomeNode` | 命中数落在 `[2, _]` 区间 |
| `loop(3,condition,action)` | `LoopNode` | 条件命中时执行动作，最多三轮 |
| `a("""{"limit":100}""")` | `ExprNode` | 为当前规则节点绑定 JSON 模板参数 |
| `_` | 命中边界 | 该侧不限制 |
| `∅` | 结构占位规则 | 稳定串并行结构，不参与业务计算 |

`&&` 和 `||` 明确保留从左到右的求值顺序及短路语义。Core 语法中的 `all` 和 `any` 接收一个或多个子规则，分别生成继承 `AndNode` 的 `AllNode` 和继承 `OrNode` 的 `AnyNode`；子类复用父类的顺序短路实现，并保留 `all(...)`、`any(...)` 的 AST 身份和稳定表达式。这种关系是单向的，不能把 `a&&b&&c` 或 `a||b||c` 反向规范化为 `all(...)`、`any(...)`。

`some(minHits, maxHits, ...)` 统计子规则命中数是否落在 `[minHits, maxHits]` 区间；`_` 表示该侧不限制。`loop(max, condition, action)` 是唯一的有界重复形式，不提供无界执行。

括号决定显式作用域。解析后不依赖文本位置，而是由 `RuleNode` 类型和父子关系承载语义。

### 2.2 `∅` 结构占位

`∅` 是结构标记，用于稳定串并行结构，不参与业务计算。例如当流程需要以并行结构开头、之后再进入串行步骤时，可用 `∅` 稳定外层串行根：

```text
∅->(a=>b)->c
```

解析结果为：

```text
SerNode(
  ∅,
  ParNode(a, b),
  c
)
```

### 2.3 内层：JavaScript 业务表达式

每个原子 `RuleDefinition` 的 `expression` 是 JavaScript，例如：

```javascript
isAdult($.name, $.age, $$)
```

也可以读取当前节点的模板参数、返回 Java 类型或对象字面量：

```javascript
$.input > $args.limit
$.amount.add(new (Java.type('java.math.BigDecimal'))('1.00'))
{stage: "CLAIM_EXTRACTION", status: "completed", claimCount: $.claimCount}
```

`RuleEngine` 会在编译边界自动为顶层对象字面量补充分组括号，规则作者不需要为避免对象被解析为代码块而手工书写 `({...})`。其他 JavaScript 表达式保持原样编译。三个运行时绑定：

| 名称 | 含义 |
| --- | --- |
| `$` | 本次规则求值的业务对象，即 `RuleVisitor.data` |
| `$$` | 本次执行的规则上下文，即 `RuleVisitor` 本身 |
| `$args` | 当前原子规则节点绑定的模板参数对象，未传参数时为空对象 |
| 顶层 UDF 名称 | `UdfContainer` 在当前作用域绑定的 UDF 函数或分组对象 |

`$`、`$$`、`$args` 具有明显的表达式符号特征，不容易与普通业务字段冲突，同时保持规则文本紧凑。

### 2.4 模板参数语法

参数化规则节点用三引号包围一段 JSON 对象文本：

```text
threshold("""{"limit":100}""") || threshold("""{"limit":300}""")
```

ANTLR4 只识别三引号参数块的安全边界，不解析 JSON 内部结构。参数不是 JavaScript 源码片段，不会被拼接或替换进规则表达式。完整语义、缓存键与边界见[第 7 节 模板参数化](#7-模板参数化)。

## 3. 节点体系

### 3.1 统一接口与节点代数

所有节点（[`node/`](../mosika-core/src/main/java/com/nianien/mosika/eval/node/) 下的 `AbstractRuleNode` 及其子类）实现：

```java
EvalResult eval(RuleContext context);
String expr();
```

并通过默认组合方法形成节点代数：

```java
and(node)
or(node)
not()
next(node)
```

默认组合方法会创建新的包装节点；已有组合节点可以协变重写为原地追加并返回自身。例如 `AndNode.and()`、`OrNode.or()`、`SerNode.next()`、`ParNode.next()` 都扩展当前节点。规则既可以由解析器构建，也可以由 Java/UI AST 直接构建。统一接口并不意味着所有节点语义相同——节点类型本身就是语义来源。

| 类别 | 节点 | 核心职责 |
| --- | --- | --- |
| 原子规则 | `ExprNode` | 根据规则 ID 调用 `RuleContext.eval()` |
| 复合规则引用 | `CompositeNode` | 为命名复合规则包裹展开后的内部规则树 |
| 逻辑节点 | `AndNode`、`OrNode`、`AllNode`、`AnyNode`、`NotNode`、`SomeNode` | 解释子节点 `matched` |
| 条件节点 | `CaseNode` | 选择并执行一个分支 |
| 执行结构 | `SerNode`、`ParNode`、`LoopNode` | 控制子节点的执行顺序、并发或有界重复 |

### 3.2 逻辑节点

**`AndNode`**：按顺序访问子节点，任一子节点 `matched=false` 立即返回未命中，全部命中返回命中；返回值表达逻辑判断，不透传某个子节点的业务 `result`。

**`OrNode`**：按顺序访问子节点，任一子节点 `matched=true` 立即返回命中，全部未命中返回未命中。

**`AllNode` 和 `AnyNode`**：`AllNode` 继承 `AndNode`，`AnyNode` 继承 `OrNode`；直接复用父类的顺序短路求值实现，分别保留 `all(...)`、`any(...)` 的节点类型和稳定表达式。`AllNode` 是 `AndNode`，`AnyNode` 是 `OrNode`；`AndNode`、`OrNode` 不会反向转换为 `AllNode`、`AnyNode`。

**`NotNode`**：访问子节点并反转其 `matched`。连续两次 `not()` 会回到原节点。

**`SomeNode`**：对应 `some(minHits, maxHits, ...)`，统计子节点命中数是否落在 `[minHits, maxHits]` 区间：

- `null` 边界对应 DSL 中的 `_`；
- Core 语法要求至少一个子规则，但允许两侧同时不设限，也允许上下界倒置或超出子规则数量；
- `SomeNode` 构造时不做边界校验：倒置区间或最小值大于子规则数直接未命中，覆盖全部可能命中数的区间直接命中；
- 当最小值已保证、最大值也不可能超出时提前返回命中；当最大值已超出或剩余节点不可能达到最小值时提前返回未命中；
- 使用 `context.visit(node)`，因此短路和详情树保持一致。

### 3.3 条件节点 `CaseNode`

`CaseNode` 先访问条件节点，只执行被选择的分支：

```text
condition=true  -> trueCase
condition=false -> falseCase
```

如果分支存在，`CaseNode` 传递该分支的 `result` 和 `matched`；如果没有对应分支，则返回 `result=null, matched=false`。这使条件节点既可以做纯判断，也可以承载动作和更复杂的流程子树。

### 3.4 执行结构

**`SerNode`（串行）**：按声明顺序访问所有非 `∅` 子节点；不因某个子节点未命中而停止；不使用最后一个子节点结果代表整个串行结构；正常完成统一返回 `result=null, matched=true`；子节点异常继续向上传播。串行结构表达“这些步骤都执行完成”，而不是逻辑与。

**`ParNode`（并行）**：使用公共执行池并发访问所有非 `∅` 分支并等待全部完成；不把子分支命中状态聚合为真假；正常完成统一返回 `result=null, matched=true`。异常契约见[第 5 节](#54-并行-parnode-的等待与异常契约)。并行结构表达“这些分支并发执行并在本层汇合”，而不是逻辑或。

**`LoopNode`（有界循环）**：对应 `loop(max, condition, action)`：

1. 每轮开始时清空当前循环的轮次缓存；
2. 求值 `condition`，未命中时退出；
3. 条件命中后求值 `action`；
4. 达到 `max` 后退出。

条件与动作共享同一轮的缓存，因此动作引用条件已求值的规则时不会重复执行；下一轮使用清空后的同一作用域，条件能重新读取动作更新后的 `$$`。嵌套循环创建各自的轮次作用域，内层循环结束后使外层当前轮次缓存失效。`max=0` 不执行条件和动作，也不影响父级缓存；循环始终受 `max` 限制，不提供无界执行形式。

### 3.5 `next()` 的协变追加语义

`RuleNode.next()` 默认创建 `SerNode`，但组合节点重写为自身追加：

```text
SerNode.next(x) -> 在串行列表末尾追加 x
ParNode.next(x) -> 在并行列表末尾追加 x
```

因此不能只根据方法名把 `ParNode.next()` 理解成“创建后续串行步骤”——它在 `ParNode` 上表示继续扩展当前并行组合。组合节点使用可变列表保存子节点，连续解析同类运算时直接追加，不做防御性复制。

### 3.6 规则引用 `ExprNode` 与复合规则根 `CompositeNode`

`ExprNode` 表示对某个规则 ID 的叶子引用，执行时把自身交给 `RuleContext.eval()`，由 `RuleEngine.evalRule()` 解析。参数化节点在构造时通过 `JsonUtils` 一次性把参数解析为 `Map<String,Object>`，并用规范化 JSON 生成完整 `expr()`。

`CompositeNode` 为命名复合规则包裹展开后的内部规则树，只表示“有名称的复合规则”，不是 Flow 类型。它的构造方法只接收 `ruleId` 和已展开的 `ruleNode`，不保存调用参数。展开机制见[第 4 节](#43-复合规则展开)。

## 4. 引擎装配

### 4.1 `RuleEngine`：注册唯一事实来源 + 预编译原子 JS

`RuleEngine` 是规则注册的单一事实来源。`RuleSuite(List<RuleDefinition>, List<UdfDefinition>)` 构造时：

1. 注册内置规则 `true`、`false`、`null`、`∅`；
2. 把全部业务 `RuleDefinition` 注册到唯一规则定义表；
3. `ruleType=0` 的原子规则预编译为 Rhino `Script`；
4. 复合规则跳过 JavaScript 编译，由外层 DSL 解析器处理；
5. 所有规则描述预编译；
6. `UdfContainer` 构建 UDF 定义树；
7. `RhinoEngine.sharedScope()` 编译并绑定全部 Java/JavaScript UDF，封闭为当前 `RuleEngine` 的共享原型作用域。

`RuleEngine` 同时承担规则注册和原子表达式编译，`NodeGenerator` 只按复合规则表构造 AST。JavaScript 语法错误在套件构造阶段暴露；普通 `ExprNode` 的 ID 查找由执行阶段的 `RuleEngine.evalRule()` 完成。

**编译缓存**——两套按源码复用的缓存和两套按规则 ID 直接读取的索引：

```text
compiledScripts   key=JavaScript expression   原子规则构造期去重及 evalExpr 运行期缓存
compiledRules     key=ruleId                  已注册原子规则脚本索引
compiledDesc      key=description text         构造期描述模板去重
compiledRuleDesc  key=ruleId                  已注册规则描述脚本索引
```

缓存值是可跨 Rhino `Context` 和线程执行的 `Script`。`compiledScripts` 使用 `ConcurrentHashMap`（`evalExpr()` 可在运行期并发加入新表达式），其余三张表在构造阶段填充。

**执行阶段**每次脚本求值：复用当前线程已进入的 Rhino `Context`（没有则通过共享 `ContextFactory` 进入一个）；创建以当前 `RuleEngine` UDF 共享作用域为原型的独立子作用域；在子作用域中绑定 `$`、`$$`、`$args`，UDF 通过原型链读取；直接执行预编译 `Script`；把 Rhino 返回值转换为 Java 值。`RuleSuite` 用 `RuleEngine.inContext()` 包住一次顶层求值，同一线程上的多段规则和描述脚本复用一个 `Context`，并行分支在工作线程中分别进入自己的 `Context`。

**Rhino 运行时**：`RhinoEngine` 维护进程级共享 `ContextFactory` 和只读标准全局作用域；每个 `RuleEngine` 另建并封闭自己的 UDF 共享作用域；每次执行再创建新的子作用域，规则顶层变量和 `globalThis` 状态不会带到下一次执行。运行时配置包括 ECMAScript 语言版本、线程安全对象支持、Java Map 属性访问、Java primitive 按 JavaScript primitive 包装、`Java.type(...)` 兼容入口。当前内核不维护 JavaScript Context 池，也不提供脚本墙钟超时；阻塞在 Java UDF 或外部调用中的执行必须由 UDF 自己控制超时。

**结果转换**：`RhinoEngine.toJava()` 在脚本结果离开当前作用域前完成转换：

```text
Wrapper      -> 原 Java 对象
CharSequence -> String
整数 Double  -> Integer / Long
NativeArray  -> ArrayList
NativeObject -> LinkedHashMap
```

先解开 Rhino `Wrapper`，因此 Java 传入并原样返回的 `BigDecimal` 等类型不会被强制降级成 JavaScript 数字。对 `Map` 和 `UdfContext` 的 JavaScript 写入也经过同一转换。

### 4.2 `NodeGenerator` 与 `NodeBuilder`：按复合规则表构造 AST

ANTLR 解析链路：

```text
DSL 文本
  -> RuleLexer / RuleParser
  -> DefaultRuleVisitor
  -> NodeGenerator
  -> RuleNode 树
```

`NodeBuilder` 直接创建 `RuleLexer`、`RuleParser` 和错误监听器；词法或语法错误由监听器直接抛出 `IllegalStateException`。`NodeBuilder.build(expr)` 是通用解析入口，只缓存构造阶段递归编译的命名复合规则；原子规则 ID、参数化原子节点和任意临时 DSL 组合每次重新解析。

`NodeGenerator` 不维护规则注册表，也不复制 `RuleEngine` 的注册状态。`DefaultRuleVisitor` 取出参数原始文本后交给 `NodeGenerator`；规则 ID 未命中复合规则表时生成 `ExprNode`，命中时展开为 `CompositeNode`。

### 4.3 复合规则展开

`ruleType=2` 的 `RuleDefinition` 的 `expression` 不是 JavaScript，而是另一段规则 ID DSL。`NodeGenerator` 遇到复合规则 ID 时：

1. 以 `CompositeNode(ruleId, ruleNode)` 保留外层规则 ID 和展开后的内部树；
2. 递归解析其内部 DSL；
3. 使用栈记录当前解析路径；
4. 遇到循环引用时立即失败；
5. 缓存编译结果，后续顶层编译或其他复合规则引用直接复用。

复合规则内部直接使用裸 `ruleId` 引用其他命名规则：该 ID 存在于复合规则表时继续展开为 `CompositeNode`，否则生成新的 `ExprNode` 并在执行时交给 `RuleEngine` 解析。判断依据只有 `ruleId`，参数不参与复合规则分类或缓存。例如：

```text
a = 1 || b
b = 2 && 3
```

形成：

```text
CompositeNode(a,
  Or(
    Expr(1),
    CompositeNode(b, And(Expr(2), Expr(3)))
  )
)
```

三者职责边界：

| 组件 | 职责 |
| --- | --- |
| `RuleEngine` | 注册全部规则，预编译原子 JavaScript，按 `ruleId` 执行叶子规则 |
| `NodeGenerator` | 根据完整复合规则表构造 AST，递归展开 `CompositeNode` 并检测循环 |
| `RuleSuite` | 组装 `RuleEngine` 和套件专属 `NodeGenerator`，建立顶层规则索引 |

### 4.4 `RuleSuite`：先收集全部复合规则再递归编译

`RuleSuite` 是规则运行快照，包含 `RuleEngine` 和 `NodeBuilder`。构造顺序：

1. 构建一个 `RuleEngine`，注册全部定义并预编译原子 JavaScript；
2. `NodeBuilder` 从完整定义列表收集所有 `ruleType=2` 的 `ruleId -> DSL`；
3. 用完整复合规则表创建套件专属 `NodeGenerator`；
4. 构造阶段遍历全部复合规则 ID，递归预编译 `CompositeNode` 并检测循环；
5. 全部完成后得到一个可执行 `RuleSuite`。

先收集、后递归编译是必要条件：复合规则可能引用另一条复合规则，也可能引用定义顺序位于其后的规则，编译不能依赖输入列表顺序。构造即完整验证——注册全部规则与 UDF、预编译原子 JavaScript 和描述模板、构建并封闭 UDF 共享作用域、递归预编译全部命名复合规则、验证语法和循环引用。构造失败不会产生半成品套件。

**发布边界**：Core 不维护全局 `current`，也不提供 `publish()`。多个套件可同时存在并相互隔离；不同套件的复合规则定义不会污染彼此。产品层如需候选验证和原子发布，应在自己的套件管理器中先构造候选对象，再替换其运行引用。命名复合规则引用没有另一套运行时机制，使用 `CompositeNode.eval()`、当前 `RuleVisitor`、既有 `matched/result` 语义及详情树。

Core 不定义 Flow、Scene 等产品抽象，也不提供 Flow 专用执行入口。产品编排只能在适配边界转换为 `ruleType=2` 的 `RuleDefinition`，并自行负责业务标识、发布状态和持久化；若产品规则与 Flow 分表存储，适配层必须把两类主键映射到互不冲突的 `ruleId` 命名空间（参考 Web 使用 `r<id>` 表示原子规则、`f<id>` 表示规则流）。

## 5. 求值与缓存

### 5.1 `RuleVisitor`：单次执行的核心上下文

每次 `RuleSuite.eval(...)` 创建新的 `RuleVisitor`。它同时承担四个角色：

```text
RuleContext     节点递归访问接口
UdfContext      UDF 可访问的规则上下文
Context Data    $$ 背后的可读写属性容器
Trace Builder   EvalNode 执行详情树构造器
```

**当前规则**：进入 `ExprNode` 时 `currentRule` 写入基础规则 ID（不含参数文本），UDF 可通过 `UdfContext.getRule()` 获知调用者。`currentRule` 使用 `ThreadLocal`，使并行分支分别维护自己的当前规则；节点退出时恢复上层规则 ID，根节点退出时删除当前线程中的值。

**共享业务上下文 `$$`**：`RuleVisitor` 继承 `AbstractMap`，数据访问代理到内部 `contextData`。JavaScript 可通过 `$$.name` 读取、`$$.name = value` 写入、`'name' in $$` 判断存在；已存在且值为 `null` 的属性保持 `null`，不存在的属性为 `undefined`。`$$.get/put/remove` 仍可用，`$$.rule`、`$$.data` 分别对应 `getRule()`、`getData()`。Map 属性写入和 `get/put/remove` 使用同步保护；并行分支共享同一份本次执行上下文。调用方传入 Map 时直接使用该对象，未传入时创建自己的 `LinkedHashMap`。`$args` 不存入该共享 Map，由当前 `ExprNode` 单独持有并在执行规则和描述时显式传递，因此一个节点的参数不会覆盖另一个节点。

### 5.2 `EvalCacheScope` 分层叶子缓存

`ExprNode.eval()` 把自身交给 `context.eval(this)`。`RuleVisitor` 读取 `node.expr()`，用当前 `EvalCacheScope.computeIfAbsent(...)` 复用同一完整叶子表达式的结果。普通节点继承父级作用域；`LoopNode` 为循环轮次建立独立作用域。这既避免同一原子规则在复合表达式中重复执行，也避免有副作用的规则或 UDF 在同一次执行中被重复触发。

缓存键约定：

| 调用形式 | 缓存键（`ExprNode.expr()`） |
| --- | --- |
| `r001` | `r001`，按裸 `ruleId` 复用叶子评估结果 |
| `r001("""{"limit":100}""")` | `r001("""{"limit":100}""")`，按含规范化 JSON 的完整表达式复用 |

非叶子节点的结果不写入缓存。每次 `visit()` 创建的 `EvalNode` 直接保存当前路径上的 `EvalResult`，同时记录该节点使用的缓存作用域；详情组装直接使用节点保存的 `EvalResult`，不依赖缓存键反查。

### 5.3 `LoopNode` 每轮独立作用域与父作用域失效

循环每轮的条件与动作共享同一个作用域，轮次切换时清空；嵌套循环拥有独立作用域。循环实际进入条件求值后会替换父作用域的内部缓存映射，使后续节点重新计算，并隔离仍可能写入旧映射的并行任务，避免循环外继续复用动作执行前的结果。

### 5.4 并行 `ParNode` 的等待与异常契约

- 使用公共执行池并发访问所有非 `∅` 分支并等待全部完成；
- 子分支异常由 `CompletableFuture` 汇集，对外抛出时解包并保留原始业务异常；
- 等待被中断时恢复当前线程的中断标记，并使用 `RuleEvalException` 表达结构执行失败；
- 等待超时或被中断时取消尚未开始执行的分支，不强制终止已在运行的分支；
- 当前实现等待上限为一分钟。

并行执行时，每个子线程先恢复并行节点对应的父执行节点，再访问自己的分支；`EvalNode.children` 使用线程安全集合保存并行分支详情。结构节点不把异常转换成“未命中”：未命中是正常业务状态，异常是执行失败，二者必须继续分离。

## 6. UDF 是内核一等能力

UDF 是内核的一等扩展机制：`mosika-core` 同时支持 JavaScript UDF 与 Java UDF 的注册、按分组/名称调用、Rhino 作用域隔离和参数分派。**是内核先支持 UDF，UI 编排层才能引用它。** 本节只讲内核机制与能力；UDF 的具体定义方式、Spring 装配和运维操作见[《运维与开发》](./运维与开发.md)。

### 6.1 `UdfDefinition` 是统一声明模型

```text
group  可选分组路径，例如 content.generation
name   UDF 名称，例如 eval
udf    Java 对象或 JavaScript 源码字符串
```

它不区分 Java UDF 和 JS UDF 的外部注册方式，类型差异由 `UdfContainer` 在装配阶段处理。分组使用点号形成多级命名空间：`new UdfDefinition("policy.sys", "replace", udf)` 在规则中调用为 `policy.sys.replace($)`。`UdfContainer` 把分组拆成嵌套 Map：

```text
policy
  └─ sys
      └─ replace
```

同名 UDF 可存在于不同分组；同一分组内名称必须唯一；一个路径位置不能同时既是函数又是子分组。`sys` 命名空间保留给内置能力。

### 6.2 `UdfContainer` 引擎中立

`UdfContainer` 只保存引擎中立的嵌套 UDF 定义树——`compile()` 产物是纯 POJO 对象图，不引用任何 Rhino 类型。Rhino 绑定由 `RuleEngine` 在构造时通过引擎提供的编译回调完成：递归创建 Rhino `NativeObject`，Java UDF 叶子绑定为 `JavaUdfFunction`，JavaScript UDF 叶子绑定为 Rhino `Function`。分组、成员和函数对象完成绑定后全部封闭，随后随当前 `RuleEngine` 只读共享。Rhino 表达式用自然属性语法访问分组（`policy.sys.replace(...)`）。

### 6.3 Java UDF 与 `UdfDelegate`

`@Udf` 负责类级别的发现、名称和分组（`value`、`group`），`@UdfMethod` 负责方法级别的暴露控制和说明（仅 `description`）；方法名、参数类型、返回类型和 varargs 标记均直接从反射签名获取，不依赖 Java 形参名是否保留。二者都是不依赖任何依赖注入框架的运行时注解——Core 本身不扫描组件或创建 UDF 实例。

`apply` 带 `@UdfMethod` 时可通过 `udf(...)` 直接调用；其他已标注方法通过 `udf.someMethod(...)` 调用；未标注方法不能被规则访问，也不出现在方法元数据中。`Functions.Function0` 到 `Function22` 只用于表达显式泛型函数签名，不是 Java UDF 的必要基类；普通 Bean 可以不实现任何函数接口，只暴露带 `@UdfMethod` 的具名方法（此时可作为具名方法容器，但不能直接当函数调用）。

Java UDF 叶子由 `UdfDelegate.Wrapper` 包装，负责：

- 只收集带 `@UdfMethod` 的 public 实例方法，排除 static、bridge 和 synthetic method；
- 按方法名和 Java 形参个数建立索引；
- 根据目标泛型参数类型转换 JavaScript 参数；
- 没有精确定长项时回退到兼容的 varargs 方法；
- 当 UDF 作为另一个 UDF 的参数传入时，根据目标参数类型传递原始 Java UDF 或统一的 Java `Function` 适配；
- 保存方法名、参数类型、返回类型、varargs 标记和说明，供运行时和展示层共用。

**同名多参在 `UdfDelegate` 下的分发**：`UdfDelegate` 不执行 Java 的按参数类型重载解析。同一方法名下，形参个数相同的签名在代理构造时被拒绝；只有方法名或形参个数不同时才能共存。调用时先查找精确定长签名，未命中再回退 varargs。例如同时声明 `apply(String, String, String)` 与 `apply(String, String...)`：三个实参精确命中定长方法，两个实参命中 varargs，更多实参在没有精确定长项时继续回退 varargs。也可以接收 `List<T>`、`Map<K,V>`、`UdfContext` 或另一个函数对象。

`JavaUdfFunction` 的直接调用和成员访问都经过同一个 `UdfDelegate`，不把原始 Java 对象交给 Rhino 做无限制成员反射。UDF 可通过参数接收 `UdfContext`，向 `$$` 写入解释性信息（如 `context.put("minAge", minAge)`），这正是规则执行和动态描述之间传递解释性信息的标准方式。

### 6.4 JavaScript UDF

当 `UdfDefinition.udf` 是字符串时：

```text
String source
  -> new JsUdf(name, source)
  -> 预编译 Rhino Script
  -> bind(当前 Context, 当前作用域)
  -> 当前作用域的 Function
  -> NativeObject 分组属性
```

源码的求值结果必须是可执行函数，支持箭头函数、匿名 `function` 表达式、函数名与注册名称一致的具名 `function`，以及定义辅助函数后返回同名入口函数的写法。匿名函数直接使用注册名称；命名函数的函数名必须与注册名称一致，否则在套件构造阶段被拒绝（例如 `function add(...)` 注册为 `sum`）。普通值表达式不能作为 UDF。

`JsUdf` 是已验证的函数定义，不实现 Java `Function`，也不持有独立执行上下文；构造时预编译并在临时 Rhino 作用域中验证源码。因此：

- JavaScript UDF 和调用它的规则在同一个当前 `Context` 中执行；
- JavaScript UDF 可通过共享作用域中已绑定的完整名称互相调用；
- 同一个 `RuleEngine` 的所有原子执行共享同一批函数对象和闭包状态；
- 分组、成员引用和函数对象均为只读，脚本不能替换 UDF 或向命名空间写入状态；
- 闭包变量和 Java UDF 实例内部状态不由 Rhino 自动变成不可变，UDF 实现必须自行保证线程安全；
- `$`、`$$`、`$args` 必须由规则表达式显式传给 UDF，不属于 UDF 的共享词法作用域——JS UDF 不能从词法作用域直接读取这三个执行期绑定。

### 6.5 内置 UDF 库（`mosika-udf`）

`mosika-udf` 模块提供一组内置 Java UDF，全部挂在保留分组 `sys` 下，按能力分类，调用形如 `sys.<类目>.<方法>`。它们的价值锚点是 JavaScript（Rhino）做不到或不可靠的能力：`double` 无法精确表示金额、`Date` 时区与解析不可靠、Rhino 没有加密能力、正则与 Unicode 语义有差异。

| 分组 | 能力 | 示例 |
| --- | --- | --- |
| `sys.num` | `BigDecimal` 精确运算 | `sys.num.divide(a, b, 2)`、`sys.num.round(x, 2)`、`sys.num.compare(a, b)`、`sys.num.percent(part, whole, 2)` |
| `sys.date` | `java.time` 日期运算（ISO `yyyy-MM-dd`） | `sys.date.plusDays(d, 3)`、`sys.date.daysBetween(a, b)`、`sys.date.dayOfWeek(d)` |
| `sys.crypto` | 摘要 / HMAC / Base64 | `sys.crypto.sha256(s)`、`sys.crypto.hmacSha256(s, key)`、`sys.crypto.base64Encode(s)` |
| `sys.text` | Java 正则 / Unicode | `sys.text.matches(s, re)`、`sys.text.replaceAll(s, re, r)`、`sys.text.normalize(s)`、`sys.text.codePoints(s)` |
| `sys.coll` | 集合运算 | `sys.coll.sum(list)`、`sys.coll.distinct(list)`、`sys.coll.contains(list, x)` |
| `sys.id` | 标识 / 随机 | `sys.id.uuid()`、`sys.id.randomInt(1, 100)` |

内置 UDF 只依赖 `mosika-core`，不含引擎或 Spring 类型；`BuiltinUdfs.definitions()` 提供不依赖框架的注册入口，参考 Web 通过 UDF 扫描把它们并入运行时套件（见[《运维与开发》](./运维与开发.md)）。数值传字符串实参可保证精确度，例如 `sys.num.add("0.1", "0.2")`。方法名 `length` 与 Rhino 函数保留属性冲突，因此文本码点计数使用 `codePoints`。

## 7. 模板参数化

模板参数化解决的是规则定义复用问题：只有阈值、等级、地域或策略参数不同的场景，无需复制多条几乎相同的 `RuleDefinition`。一条原子规则定义作为可复用模板，在同一棵规则树中由不同节点绑定不同参数。

```text
多条重复定义：            一条模板定义：
r1 = $.input > 100        threshold = $.input > $args.limit
r2 = $.input > 200
r3 = $.input > 300
```

调用方在规则 ID DSL 的原子节点上绑定参数：

```text
threshold("""{"limit":100}""") || threshold("""{"limit":300}""")
```

这样保持两个边界：规则定义仍只负责表达稳定业务逻辑，每个规则节点只负责提供本次调用的配置参数。

### 7.1 `$args` 声明与绑定

原子规则用 `$args` 读取本次实例化的局部配置，与 `$`、`$$` 共享同一组绑定：

| 名称 | 生命周期 | 含义 |
| --- | --- | --- |
| `$` | 本次顶层执行 | 业务输入对象，即 `RuleVisitor.data` |
| `$$` | 本次顶层执行 | 共享的可变规则上下文，即 `RuleVisitor` |
| `$args` | 当前原子规则节点 | 当前节点绑定的模板参数对象 |

未传模板参数时，`$args` 绑定为空对象，规则照常使用 `$` 和 `$$`。

编译与执行链路：

```text
atomicRuleId("""{...}""")
  -> Rule.g4 / DefaultRuleVisitor
  -> NodeGenerator 按 ruleId 查询复合规则表
     └─ 未命中 -> ExprNode(ruleId, arguments)
  -> RuleVisitor.eval(ExprNode)
  -> RuleEngine.evalRule(ruleId, target, context, arguments)
  -> Rhino scope: $ / $$ / $args / UDF
  -> EvalResult
  -> 当前 EvalNode
```

规则 JavaScript `Script` 按 `RuleDefinition.expression` 预编译并复用；每次执行在独立 Rhino 作用域中把当前节点参数作为 `$args` 绑定进去，因此不需要为每组参数重新编译 JavaScript。参数不参与原子节点的编译，也不改变 `RuleDefinition`。节点实例在 DSL 解析时已确定参数，所以同一个模板规则可以在一棵执行树中出现多次。

参数约束：根值必须是 JSON 对象（不能是数组、字符串、数字或 `null`）；空参数和不合法 JSON 在节点构建阶段直接失败；`expr()` 把参数规范化为紧凑 JSON，保证节点表达式可重新解析。

### 7.2 规范化 JSON 缓存键

参数化规则涉及三层复用边界：

- `NodeBuilder` 只缓存按唯一 ID 预编译的 `CompositeNode`，不缓存原子 `ExprNode` 或原子参数变体；
- `RuleVisitor` 在当前求值作用域内使用 `ExprNode.expr()` 作为叶子结果缓存键；
- `RuleEngine` 按稳定的 `RuleDefinition.expression` 复用 JavaScript `Script`，节点参数只在执行时绑定为 `$args`。

`ExprNode` 在构造时通过 `JsonUtils` 一次性把参数解析为 `Map<String,Object>`，并用规范化 JSON 生成完整 `expr()`；执行阶段不再重复解析或规范化。**对象字段在所有嵌套层级递归排序，数组元素顺序保留。** 对象字段顺序不影响 `expr()`，数组元素顺序不同会分别求值。这样既避免只按 `ruleId` 缓存造成参数串用，也保持相同参数结构在当前求值作用域中的结果复用语义。

### 7.3 一次顶层执行内相同参数只求值一次；执行详情不合并

参数完全相同时，下面两次调用只真正求值一次：

```text
r001("""{"limit":100}""")->r001("""{"limit":100}""")
```

但两个调用仍分别生成执行节点，并保存各自的结果和动态描述——参数化调用的执行详情不合并。每个 `EvalNode` 保存当前执行路径上自己的 `EvalResult`，因此同一规则的多次参数化调用在详情阶段各自使用自己保存的 `EvalResult`，不按 `ruleId` 查找并合并结果。

`loop(max, condition, action)` 为每个循环建立轮次作用域：条件与动作在同一轮共享缓存，下一轮重新求值；嵌套循环使用各自的轮次作用域；循环实际求值后使父级缓存失效，避免循环外继续复用动作执行前的参数化规则结果。

### 7.4 边界

模板参数只对原子 `ExprNode` 具有执行语义。复合规则由唯一 `ruleId` 标识，一个 ID 对应一棵预编译规则树：

```text
f1 = a("""{"x":1}""") && b("""{"y":2}""") && c
```

参数分别属于原子规则 `a` 和 `b`，`f1` 本身只通过裸 ID 引用。`CompositeNode` 的构造方法只接收 `ruleId` 和已展开的 `ruleNode`，其自身不保存调用参数；`NodeBuilder` 也只按 `ruleId` 缓存这一份 `CompositeNode`。外层通用 ID 语法即使写成 `f1("""{...}""")`，命中复合规则表后仍返回同一个缓存节点，不会创建新的复合规则定义或参数变体，参数也不会向内部原子规则传播。受支持的复合规则引用形式是裸 `f1`。

`$args` 是运行时保留顶级名称，用户 UDF 不能覆盖它。参数化调用的可视化配置属于产品层编辑能力（见[《规则编排交互设计》](./规则编排交互设计.md)），不改变 Core 的参数绑定契约。

## 8. 执行详情与动态描述

### 8.1 规则描述也是可执行表达式

`RuleDefinition.desc` 不是静态注释，而是使用同一份 `$`、`$$`、`$args` 执行的简化规则表达式，主要用于生成可解释的执行详情：

```java
new RuleDefinition(
    "101",
    "isAdult($.name,$.age,$$)",
    "${$.name}的年龄(${$.age})小于${$$.get('minAge')}岁"
)
```

执行顺序：执行规则 `expression` → UDF 通过 `$$` 写入 `minAge` 等上下文属性 → `RuleVisitor` 构造执行详情 → 使用当前 `$` 和 `$$` 执行 `desc` → 生成 `RuleResult.desc`。因此描述能引用规则执行过程中写入的上下文，而不需要把诊断字段塞进业务 `result`。

描述采用标准 JavaScript 模板插值 `${...}`：

```text
${$.name}
${$$.get('agent')}
${$args.minAge}
${$.name.toUpperCase()}
```

`compileDesc()` 使用 `String.raw` 模板字符串编译为 Rhino `Script`，既保留静态文本中的反斜杠和换行，又让 `${...}` 内保持完整 JavaScript 语义（方法调用、对象字面量、正则表达式），描述不退化成只支持属性替换的模板。

### 8.2 执行详情树

每次 `visit(node)` 都创建 `EvalNode` 并挂到当前父节点。非叶子节点进入时更新 `currentEval`，退出时在 `finally` 中回溯——保证异常路径不会把后续节点挂到错误父节点。根节点退出和并行任务结束时删除工作线程中的 `ThreadLocal` 状态。并行执行时每个子线程先恢复并行节点对应的父执行节点，再访问自己的分支；`EvalNode.children` 使用线程安全集合保存并行分支详情。

执行结束后 `getRuleResults()` 将 `EvalNode` 树转换为 `RuleResult` 树：从每个 `EvalNode` 直接读取该次执行的节点结果；对原子规则和命名复合规则求值描述，渲染期间将 `currentRule` 限定为正在物化的规则 ID，把同一节点参数绑定为 `$args`，结束后恢复原值；递归附加 `subRules`；保留真实短路后的访问路径，而不是静态 AST 全量展开。因此详情表达“本次实际执行了什么”，而不是“理论上可能执行什么”。

### 8.3 结果模型

**`EvalResult`** 字段：

| 字段 | 含义 |
| --- | --- |
| `expr` | 当前节点或规则表达式 |
| `result` | 业务返回值 |
| `matched` | 作为条件时的命中状态 |

普通 JavaScript 返回值通过默认规则转换为 `matched`：

| 返回值 | 命中规则 |
| --- | --- |
| `null` | 未命中 |
| `Boolean` | 使用原值 |
| `Number` | 大于零时命中 |
| `String` | `no/false/null/0/fail` 视为未命中，其余命中 |
| `Collection` | 非空时命中 |
| `Map` | 非空时命中 |
| 其他对象 | 命中 |

数字判定按具体数值类型精确比较：`BigDecimal` 和 `BigInteger` 使用 `signum()`，整数类型使用 `longValue()`，其他数字使用 `doubleValue()`，避免把任意 `Number` 统一缩窄后再判定。结构节点和部分逻辑节点可以使用显式构造函数分别指定 `result` 与 `matched`，不依赖默认转换。

**`RuleResult`** 继承 `EvalResult`，增加 `desc`（动态规则描述）和 `subRules`（实际执行的子规则详情）。它属于可解释性模型，不改变业务返回值。

**`NodeResult`** 是 `RuleSuite` 对外返回模型，包含 `expr`（根节点 DSL）、`result`（根节点业务结果）、`details`（执行详情）。带外部上下文的求值入口直接把调用方提供的 Map 作为 `RuleVisitor` 的共享上下文，规则通过 `$$` 写入的中间结果直接保留在该 Map 中，不需要执行后复制。

**`NaResult`** 是区别于 Java `null` 的“无业务结果”哨兵，内置 `null` 和 `∅` 规则返回该对象。`RuleSuite` 发现根节点结果本身是 `NodeResult` 时直接返回，使 `NaResult` 这类哨兵能穿过普通 `EvalResult` 包装。

## 9. 规则类型、内置规则、监听与异常

### 9.1 规则类型 `ruleType=0/2`

Core 只有一种声明态 `RuleDefinition`，规则类型字段为 `ruleType`，常量在 [`RuleDefinition`](../mosika-core/src/main/java/com/nianien/mosika/engine/RuleDefinition.java)：

```text
RULE_TYPE_ATOMIC = 0
  ruleId + JavaScript expression
            │ compile
            ▼
         ExprNode

RULE_TYPE_COMPOSITE = 2
  ruleId + rule ID DSL
            │ recursive compile
            ▼
  CompositeNode(ruleId, DSL root)
```

原子规则和复合规则共享 `ruleId` 命名空间、查找 API 和执行入口。

### 9.2 内置规则

`RuleEngine` 构造时注册内置规则 `true`、`false`、`null`、`∅`。`null` 和 `∅` 返回 `NaResult` 哨兵；`∅` 是结构占位标记，不参与业务计算。

### 9.3 监听事件

`RuleEvent.EventType` 定义：

```text
PARSE_SUCCEED
PARSE_FAIL
EVAL_SUCCEED
EVAL_FAIL
```

求值链路由 `RuleVisitor` 发送 `EVAL_SUCCEED` 和 `EVAL_FAIL`。`PARSE_SUCCEED`、`PARSE_FAIL` 及 `RuleListener.onParse()` 属于监听器接口，内置 DSL 解析链路只发送求值事件。事件携带表达式、结果或异常及耗时；监听器不参与节点语义和业务结果。每个监听器独立通知：单个监听器抛出 `RuntimeException` 时记录告警并继续通知其他监听器，不影响规则解析或执行。

### 9.4 异常类型

| 异常 | 边界 |
| --- | --- |
| `IllegalStateException` | 当前 `NodeBuilder` 的 DSL 词法、语法或复合规则循环失败 |
| `RuleParseException` | 解析异常类型，供外部解析入口使用；内置 DSL 解析以 `IllegalStateException` 报错 |
| `RuleEvalException` | 规则 JavaScript/UDF 执行失败，或并行节点中断、超时等结构执行失败 |
| `RuleMatchException` | 规则匹配异常类型 |

结构节点不把异常转换成“未命中”。规则未命中是正常业务状态，执行异常是失败，二者必须继续分离，异常正常向上传播。

## 10. 核心不变量

1. 原子业务表达式使用 JavaScript，规则结构使用规则 ID DSL；不要混成一套自定义脚本语言。
2. `$` 始终表示本次业务输入，`$$` 始终表示本次规则上下文，`$args` 始终表示当前原子规则节点的模板参数。
3. `matched` 是逻辑/控制状态，`result` 是业务值。
4. `AndNode/OrNode/AllNode/AnyNode/NotNode/SomeNode` 解释命中状态；`SerNode/ParNode` 只控制执行。
5. `SerNode/ParNode` 正常完成返回 `result=null, matched=true`。
6. 规则未命中不是异常，执行异常不能被吞成未命中。
7. `RuleNode` 及其递归组合是执行语义唯一来源。
8. `∅` 是结构标记，不参与业务计算。
9. UDF 分组由 `UdfContainer` 引擎中立地构建（`compile()` 产物为纯 POJO 对象图），Rhino 绑定由 `RuleEngine` 通过编译回调完成并封闭为只读共享；`JsUdf` 校验函数源码并在 `RuleEngine` 构造期绑定共享函数。
10. Java UDF、泛型参数转换和 Java UDF 作为参数继续走统一 `UdfDelegate`；Java UDF 只暴露 `@UdfMethod` 方法并按方法名与参数个数分派，JavaScript UDF 与调用规则在同一个当前 Rhino Context 中执行。
11. Java 互操作、Host Object 和 `BigDecimal` 属于可信规则能力。
12. 一个 `RuleSuite` 装配一个 `RuleEngine`；运行请求创建新的 `RuleVisitor`。
13. `RuleSuite` 必须完整构造成功才能交给产品层发布，Core 不维护全局发布状态。
14. 命名复合规则只按唯一 `ruleId` 在套件构造阶段解析为 `CompositeNode`，保留完整子详情并统一检测循环引用；复合规则自身没有参数变体。
15. Core 不定义 Flow、Scene 等产品抽象；产品编排只能在适配边界转换为复合 `RuleDefinition`。
16. 描述保留完整 JavaScript 表达式能力，不退化成只支持属性替换的模板。
17. 叶子结果按 `ExprNode.expr()` 复用：无参数时为裸 `ruleId`，参数化时包含规范化 JSON；每次节点访问保留独立详情。

## 11. 完整执行示例

定义：

```java
RuleDefinition adult = new RuleDefinition(
    "101",
    "ageAtLeast($.age,$args.minAge,$$)",
    "${$.name}的年龄为${$.age}岁，本次阈值为${$args.minAge}岁"
);

RuleDefinition allow = new RuleDefinition("allow", "'ALLOW'", "允许");
RuleDefinition reject = new RuleDefinition("reject", "'REJECT'", "拒绝");

RuleDefinition userCheck = new RuleDefinition(
    "user-check",
    "101(\"\"\"{\"minAge\":18}\"\"\")?allow:reject",
    "用户准入复合规则",
    RuleDefinition.RULE_TYPE_COMPOSITE
);
```

UDF：

```java
class AdultUdf implements Functions.Function3<Integer, Integer, UdfContext, Boolean> {
    @UdfMethod(description = "校验用户年龄门槛")
    public Boolean apply(Integer age, Integer minAge, UdfContext context) {
        context.put("checkedMinAge", minAge);
        return age >= minAge;
    }
}
```

创建套件与输入：

```java
RuleSuite suite = new RuleSuite(
    List.of(adult, allow, reject, userCheck),
    List.of(new UdfDefinition("ageAtLeast", new AdultUdf()))
);
Map<String, Object> user = Map.of("name", "jack", "age", 20);
```

装配：

```text
RuleSuite
  ├─ RuleEngine
  │    ├─ 101 -> Rhino Script
  │    ├─ allow -> Rhino Script
  │    ├─ reject -> Rhino Script
  │    └─ UDF shared scope -> ageAtLeast -> UdfDelegate(AdultUdf)
  └─ user-check -> CompositeNode(
         user-check,
         CaseNode(101("""{"minAge":18}"""), allow, reject))
```

执行 `suite.eval("user-check", user)`：

```text
1.  RuleSuite 取得已编译的 CompositeNode，并创建 RuleVisitor(user)
2.  RuleSuite 进入 Rhino Context
3.  visit CompositeNode -> CaseNode -> ExprNode("101", {minAge:18})
4.  RuleVisitor.eval("101", arguments)
5.  RuleEngine 为当前脚本创建独立子作用域
6.  绑定 $=user、$$=RuleVisitor、$args={minAge:18}，通过共享原型解析 ageAtLeast UDF
7.  执行 ageAtLeast($.age,$args.minAge,$$)
8.  UDF 调用 context.put("checkedMinAge", 18)，并返回 Boolean
9.  EvalResult 根据返回值生成 matched
10. CaseNode 选择并执行 allow
11. 使用各节点执行时的 $、$$、$args 渲染描述并转换 EvalNode 详情树
12. 返回 NodeResult
```

该链路体现关键分工：DSL 负责选择和编排；JavaScript 负责业务计算；`$args` 负责把模板规则实例化为当前节点；UDF 负责扩展和上下文协作；`matched` 负责控制；`result` 负责业务返回；`RuleResult` 负责解释。

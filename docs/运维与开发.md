# 运维与开发

> 适用模块：`mosika-web`、构建与部署

本文聚焦工程结构、构建测试、运行部署以及 UDF 的定义与使用。内核语义（DSL、执行树、结果契约、UDF 引擎内部机制）见《[规则模型核心设计](规则模型核心设计.md)》；UI 编排与画布交互见《[规则编排交互设计](规则编排交互设计.md)》。

## 1. 环境与工程结构

- JDK 21、Maven 3.9 或兼容版本。
- 启动脚本额外依赖 `curl` 和系统端口查询工具（`lsof` 或 `ss`），可执行 `./scripts/mosika.sh doctor` 检查环境。
- JavaScript 表达式在标准 JDK 21 上通过 Rhino 运行。

多模块划分（`pom.xml` 中声明的构建顺序即依赖顺序）：

| 模块 | 职责 | 依赖 |
| --- | --- | --- |
| `mosika-core/` | DSL、执行树、执行上下文、结果模型、UDF 抽象与命名原子/复合规则；不含 Spring 依赖 | 无内部依赖 |
| `mosika-udf/` | Java UDF 实现（含内置 UDF），由 Starter 按配置扫描注册 | `mosika-core` |
| `mosika-spring-boot-starter/` | Spring Boot 自动配置：`@Udf` Bean 扫描与 `UdfDefinition` 装配入口 | `mosika-core`、`mosika-udf` |
| `mosika-ui/` | 可序列化 UI AST，以及 UI 树到内核 `RuleNode` 的单向编译 | `mosika-core` |
| `mosika-web/` | Spring Boot 管理服务、Flow 产品模型、SQLite 持久化、REST 和静态编辑器 | `mosika-ui`、`mosika-spring-boot-starter` 及其传递依赖 |

模块边界为强约束：`mosika-core` 只认识 `RuleDefinition` 与 `UdfDefinition`，不含页面、持久化或 Flow 产品模型；`mosika-ui` 只做单向编译，不反推 UI 树；`mosika-web` 是可选的参考控制面，不承载规则语义或执行内核。模块边界与协作约束详见根目录 [`AGENTS.md`](../AGENTS.md)。

ANTLR 语法位于 `mosika-core/src/main/antlr4/Rule.g4`，`mvn` 构建时自动生成到 `target/generated-sources/`。不要修改生成代码，语法变更需重跑构建并补充回归测试。

## 2. 构建与测试

完整验证（先重新生成 ANTLR 源，再运行全部测试）：

```bash
mvn clean test
```

按模块验证（`-am` 同时构建其依赖模块）：

```bash
mvn -pl mosika-core test
mvn -pl mosika-udf -am test
mvn -pl mosika-spring-boot-starter -am test
mvn -pl mosika-ui -am test
mvn -pl mosika-web -am test
```

单类 / 单方法：

```bash
mvn -pl mosika-core test -Dtest=SomeTest
mvn -pl mosika-core test -Dtest=SomeTest#someMethod
```

生成全部制品：

```bash
mvn clean package
```

测试为 JUnit 5，命名 `*Test`。修改解析、执行、并发上下文或 UI 树转换时应补充对应回归测试。仅修改文档时无需全量测试，但须检查链接与 Markdown/SVG 完整性。

## 3. 运行与部署

统一通过启动脚本操作，覆盖构建、启停、状态与日志：

```bash
./scripts/mosika.sh doctor    # 检查 JDK、Maven、curl、端口工具等环境
./scripts/mosika.sh build     # 构建 mosika-web 可执行 JAR
./scripts/mosika.sh start     # 构建并后台启动
./scripts/mosika.sh status    # 查看运行状态
./scripts/mosika.sh logs      # 查看日志
./scripts/mosika.sh restart   # 重启
./scripts/mosika.sh stop      # 停止
./scripts/mosika.sh dev       # 前台开发模式
```

完整参数以 `./scripts/mosika.sh help` 的当前输出为准。

### 环境变量

| 环境变量 | 默认值 | 含义 |
| --- | --- | --- |
| `MOSIKA_PORT` | `8080` | 服务端口 |
| `MOSIKA_SERVER_ADDRESS` | `127.0.0.1` | 监听地址 |
| `MOSIKA_DB_PATH` | `mosika-web/data/mosika.db` | SQLite 数据库路径 |
| `MOSIKA_RUN_DIR` | `${TMPDIR:-/tmp}/mosika` | 运行状态与日志目录 |
| `MOSIKA_START_TIMEOUT` | `60` | 启动检查超时秒数 |
| `MOSIKA_STOP_TIMEOUT` | `15` | 停止等待秒数 |
| `MOSIKA_JAVA_OPTS` | 空 | 额外 JVM 参数 |

运行状态文件与日志默认写入 `MOSIKA_RUN_DIR`（`${TMPDIR:-/tmp}/mosika/`），不会写入仓库。SQLite 属于 Web 参考实现，默认位于 `mosika-web/data/mosika.db`；仓库跟踪一份可直接试用的演示数据库，但不跟踪 WAL、SHM、journal 等运行时文件。运行态、日志与 SQLite 都不得写进仓库目录。

### restart 的实例定位

`restart` 不依赖运行状态文件来判定要重启哪个进程。它按「端口 + 命令行」定位实例：凡是占用目标端口、且命令行匹配 `mosika-web` 可执行 JAR 的进程一律结束，然后清理状态并重新启动。因此手动 `java -jar` 启动、或状态文件丢失的游离实例同样会被正确接管重启。若存在受管状态，会沿用其记录的端口与数据库路径；另一 checkout 的状态则拒绝接管。

## 4. 页面入口与路由

`mosika-web` 采用无构建工具的多页面结构，页面源码位于 `mosika-web/src/main/resources/static/ui/`，由 Spring Boot 标准静态资源规则发布为 `/ui/**`。`WebConfig`（`mosika-web/src/main/java/.../WebConfig.java`）只负责简洁路由的 `forward`，保留浏览器地址，页面内静态资源统一用 `/ui/` 绝对引用。

| 路由 | 目标页 | 含义 |
| --- | --- | --- |
| `/` | `console.html` | 产品首页 / 控制台 |
| `/scenes` | `scenes.html` | 业务场景与版本列表 |
| `/namespaces` | `namespaces.html` | 命名空间选择门禁与管理 |
| `/rules` | `rules.html` | 原子规则库 |
| `/udfs` | `udfs.html` | UDF 注册中心 |
| `/flow/{flowId}` | `index.html` | 规则流画布（`flowId` 形如 `f<数字>`，由前端解析） |
| `/flow` | 重定向到 `/scenes` | 缺 id 时回列表 |

健康检查为 `GET /api/health`。

跨页基础能力集中在以下共享文件，页面自身只保留布局与业务交互：

| 文件 | 职责 |
| --- | --- |
| `tokens.css` | 品牌色、语义色、间距、圆角、阴影、字体等设计令牌 |
| `ui-common.css` | 顶部导航、页头、按钮、表单、表格、状态、弹窗与响应式规则 |
| `ui-common.js` | HTML 转义、查询、节流/防抖、Toast、按钮忙碌态等通用交互 |
| `code-editor.js` | JavaScript 表达式解析与格式化的共享配置 |
| `api.js` | Web API 请求封装 |
| `ns.js` | 命名空间选择、路由参数与跨页导航 |
| `treenode.js` | 前端 UI AST 的构造、遍历与序列化 |

新增跨页样式或行为时应先判断能否进入共享文件，避免在多个 HTML 中复制颜色、控件状态、Toast、转义或编辑器配置。

## 5. 定义与使用 Java UDF

`mosika-core` 保持无 Spring 依赖，UDF 的注解声明与 Spring 装配由 `mosika-spring-boot-starter` 承担。

### 注解声明

- `@Udf` 标注 UDF 类，声明名称（`value`）与分组（`group`）。
- `@UdfMethod` 标注规则可调用的方法及其说明；未标注的方法不会被规则访问。

UDF 类无需再加 `@Component`，也无需实现 `Function` 接口：

```java
@Udf(group = "account", value = "profile")
public class NormalizeAccountUdf {

    private final AccountService accountService;

    public NormalizeAccountUdf(AccountService accountService) {
        this.accountService = accountService;
    }

    @UdfMethod(description = "标准化账户信息")
    public Account normalize(Account account) {
        return accountService.normalize(account);
    }
}
```

上述方法通过 `account.profile.normalize(...)` 调用。若需 `account.profile(...)` 直接调用，则暴露一个带 `@UdfMethod` 的 `apply` 方法。未显式设置 `value` 时，名称取类短名并按 JavaBean 规则转换首字母（`NormalizeAccountUdf` → `normalizeAccountUdf`）；`group` 保持 `@Udf` 声明的点分隔路径。

### 扫描范围配置

默认扫描 Spring Boot 自动配置基础包（通常是 `@SpringBootApplication` 所在包及其子包）。外部依赖中的 UDF 通过 `mosika.udf.scan-packages` 追加扫描包（该属性由 `UdfBeanDefinitionRegistrar` 读取）：

```yaml
mosika:
  udf:
    scan-packages:
      - com.example.risk.udf
      - com.example.marketing.udf
```

配置包与默认包合并扫描，允许父子包重叠；抽象类与接口不会被注册。外部 UDF 只需添加 `@Udf`，无需由外部依赖提供自动配置。

### 内置 UDF 库

`mosika-udf` 提供一组内置 Java UDF（`com.nianien.mosika.udf.builtin` 下的 `Sys*Udf`），全部挂在保留分组 `sys` 下，按能力分类：`sys.num`（精确数值）、`sys.date`（日期）、`sys.crypto`（哈希编码）、`sys.text`（文本）、`sys.coll`（集合）、`sys.id`（标识）。参考 Web 的 `application.yml` 默认把该包加入 `mosika.udf.scan-packages`，因此内置 UDF 随应用启动被扫描注册，与业务 Java/JavaScript UDF 一起进入运行时套件；非 Spring 场景可用 `BuiltinUdfs.definitions()` 直接获取定义。完整目录与调用示例见[《规则模型核心设计》](规则模型核心设计.md#65-内置-udf-库mosika-udf)。

### Spring 自动装配

装配链由 `mosika-spring-boot-starter` 提供：

| 类 | 职责 |
| --- | --- |
| `MosikaUdfAutoConfiguration` | 导入扫描注册器，并提供 `SpringUdfLoader` Bean |
| `UdfBeanDefinitionRegistrar` | 扫描默认包与 `mosika.udf.scan-packages` 扩展包，注册尚不存在的 `@Udf` Bean |
| `SpringUdfLoader` | 从每个 `@Udf` Bean 生成受控代理并映射为 Core `UdfDefinition` |

与容器已有 Bean 的关系：Starter 在配置类解析完成后扫描 UDF。若同类型已通过 `@Bean`、`@Component` 等存在于容器中，直接复用已有 Bean，不额外创建；否则将 `@Udf` 类型注册为 Spring Bean。两种方式都走主容器完成依赖注入与后置处理。需要显式控制创建过程时，可同时提供 `@Bean` 工厂方法：

```java
@Bean
NormalizeAccountUdf normalizeAccountUdf(AccountService accountService) {
    return new NormalizeAccountUdf(accountService);
}
```

`SpringUdfLoader.loadUdfs()` 每次返回当前容器中全部 `@Udf` Bean 对应的 `UdfDefinition`：它把 Spring 管理的 Bean 包装为 `UdfDelegate` 放入 `UdfDefinition.udf`；方法注解、参数与返回类型从 AOP 目标类读取，真正调用仍落在 Spring 代理 Bean 上，因此构造器注入、Bean 生命周期与 AOP 拦截都会保留。UDF 路径唯一性、分组冲突与函数签名校验由 Core 在 `RuleSuite` 构造阶段统一处理。

应用侧把 UDF 装进 `RuleSuite` 的典型写法如下：

```java
@Bean
RuleSuite ruleSuite(RuleRepository repository, SpringUdfLoader udfLoader) {
    return new RuleSuite(repository.loadRules(), udfLoader.loadUdfs());
}
```

> 说明：示例中的 `RuleRepository` 是**应用自备的示例类型**，代表「应用如何获取自己的规则来源」，本项目并不发布该类。规则来源与套件生命周期由应用负责——Starter 只处理 Java UDF Bean，不决定规则从文件、数据库还是配置中心获取，也不自动创建或刷新 `RuleSuite`。

### 合并进运行时套件

在参考 Web 中，`RuleSuiteManager`（`mosika-web/src/main/java/.../service/RuleSuiteManager.java`）负责组装并热刷新全局唯一的 `RuleSuite`：运行时**先加载全部 Java UDF，再追加当前命名空间已启用的 JavaScript UDF**，两类定义一起交给 Core。因此规则表达式可直接跨类型组合调用：

```javascript
account.normalize(databaseFns.enrich($))
```

## 6. 使用 JavaScript UDF

JavaScript UDF 通过 Web 控制台的 `/udfs` 注册中心定义与管理，存储在 SQLite `udf_definition` 表，按数据库命名空间隔离，可创建、编辑、停用与启用。查询、只读展示与冲突处理由 `UdfDefinitionService`（`mosika-web/src/main/java/.../service/UdfDefinitionService.java`）承担。

两类 UDF 在同一份查询结果与运行时套件中合并呈现：

| 属性 | Java UDF | JavaScript UDF |
| --- | --- | --- |
| 来源 | Spring 容器中的 `@Udf` Bean | SQLite `udf_definition` |
| 命名空间 | 对所有启用命名空间可用 | 按数据库命名空间隔离 |
| 运行状态 | 随应用启动始终启用 | 可启用或停用 |
| 修改方式 | 只能改 Java 代码与 Spring 配置 | 可通过 Web 增删改停启 |
| 查询标记 | `type=java`、`editable=false` | `type=javascript`、`editable=true` |
| 数据库字段 | 无 ID、版本、时间 | 含 ID、乐观锁版本与时间 |

查询时 Java UDF 排在数据库 UDF 之前，共同参与 `total`、`pageNumber`、`pageSize` 分页；`status=0` 不返回 Java UDF；关键字可匹配 Java UDF 的完整路径、实现类名、方法名、方法说明与参数/返回类型。

创建、更新或启用 JavaScript UDF 时，若完整路径与任一 Java UDF 相同，接口返回 `409`，数据库记录与运行时套件都不会被替换。页面据 `editable` 隐藏 Java UDF 的编辑与启停操作，并在只读详情中展示实现类、暴露方法签名与说明（`udfs.html`）。

## 7. UDF 定位

UDF 是**进程内可执行代码，而非不可信配置**：Java UDF 是容器托管的 Bean，JavaScript UDF 也在服务进程内以受控方式执行。`sys` 命名空间保留给内置函数——创建 JavaScript UDF 时 `group` 为 `sys` 或以 `sys.` 开头会被拒绝，`$`、`$$`、`$args`、`sys` 等顶层名同样保留。UDF 的命名解析、内置函数与引擎内部机制详见《[规则模型核心设计](规则模型核心设计.md)》。

## 变更验证边界

- Core：沿 `Rule.g4 → DefaultRuleVisitor → RuleNode.eval() → 测试` 验证语义。
- UI AST：检查 `toRule()`、`TreeNode.visit()`、`NodeTypeResolver` 与 JSON 往返。
- UDF 装配：`MosikaUdfAutoConfigurationTest` 覆盖默认/扩展包扫描、构造器注入、JDK/CGLIB 代理调用、`@Bean` 复用与重复注册规避；`MosikaJavaUdfIntegrationTest` 覆盖 Web 合并分页、方法元数据、只读标记、Java/JavaScript 联合执行与路径冲突回滚。
- Web：检查控制器、持久化、静态资源路由，并执行 `mvn -pl mosika-web -am test`。
- 浏览器交互变更不能只用 Java 测试证明，需在真实页面验证选择、弹窗、拖拽、保存与错误态。

# 规则编排交互设计

> 适用模块：`mosika-ui`、`mosika-web`

本文档阐述可视化规则编排层的设计。规则语法、节点语义与执行引擎见[规则模型核心设计](./规则模型核心设计.md)；部署与 UDF 操作见[运维与开发](./运维与开发.md)。

## 1. 设计特色

### 1.1 规则定义与规则编排解耦

Mosika 把「一条规则是什么」和「多条规则如何编排」拆成两件事：

- **规则定义**属于内核：一条原子规则是 `RuleDefinition`，由 `ruleId` 稳定标识，内容是 JavaScript 表达式或规则 ID DSL。编排层只持有对 `ruleId` 的引用（`AtomicNode.expr`），不复制规则内容。
- **规则编排**属于 UI 层：串行、并行、分支、顺序、循环只描述「这些规则以什么结构执行」，不关心规则内部实现。

解耦带来的直接收益：同一条原子规则可以被任意场景复用；改规则内容不动编排，改编排不碰规则；编排层能引用的原子规则与 UDF 都由内核提供（见 [1.4](#14-编排层引用内核能力)），UI 只做结构组合。

### 1.2 递归树统一串 / 并 / 分支 / 顺序 / 循环

编排结构是一棵递归树，只有两个递归域：

- **Flow（宿主）**：动作、条件、串行、并行、分支、循环
- **Rule（内嵌规则）**：原子引用、可取反引用、与或组合、限定匹配

```text
Flow = ActionNode(rule, next?)
     | ConditionNode(rule, next?)
     | SerialNode(Flow+)
     | ParallelNode(Flow+)
     | DecisionNode(ConditionNode+, default?)
     | LoopNode(max, rule, next)

Rule = AtomicNode(expr, args?)
     | BooleanNode(expr, args?, negative)
     | LogicNode(&& | ||, Rule+)
     | MatchNode(minHits, maxHits, Rule+)
```

两个递归域只通过 `FlowNode.rule -> RuleNode` 单向连接，规则子树不能引用 Flow 节点，因此规则表达式不会反向携带编排关系。

### 1.3 递归带来的概念一致性

用递归树而不是自由连线的 DAG，换来的是概念上的统一，消除了两类需要额外设计的边界问题：

- **不需要设计流程交汇点**。每个 `SerialNode`、`ParallelNode`、`DecisionNode` 都是自身子树的一等虚拟根，任意 `FlowNode` 都能作为它的一个分支，任意同类子树可互相替换。并行分支各自是一棵完整 Flow 子树，在本层「并发执行并汇合」由结构本身表达，不需要在画布上把多条分支手工连回同一个汇合节点，也就不会退化成必须维护合流点的 DAG。
- **不需要定义循环体边界**。循环体就是 `LoopNode.next` 指向的一棵普通 Flow 子树，单根、可嵌套任意结构，天然自带边界。循环不是一种特殊连线，而是和串并分一样的递归节点，因此 `loop` 可以自然嵌套 `loop`，无需为「循环从哪开始、到哪结束」单独设计语义。

结构是显式声明的，不从画布布局、坐标或连线方向推断。`SerialNode(ParallelNode(a,b), ParallelNode(c,d))` 直接表示「先跑完第一组并行，再跑第二组」，布局方向只服务阅读。

### 1.4 编排层引用内核能力

编排层能做的一切都建立在内核能力之上：

- **原子规则与复合场景**：动作节点引用动作类原子规则或已发布业务场景，条件节点引用条件类原子规则，均以 `ruleId` 引用。
- **JS / Java UDF**：内核同时支持 JavaScript 与 Java UDF，规则表达式可直接调用。是内核先支持了 UDF，编排层才谈得上「在规则里调用函数」。UDF 的内核机制见[规则模型核心设计](./规则模型核心设计.md)，定义与装配见[运维与开发](./运维与开发.md)。

### 1.5 UI 配置单向编译为 DSL、在线测试与执行路径渲染

- **UI → DSL 单向编译**：UI 树经 `UINodeAdapter.toRule()` 单向编译为内核 `RuleNode` 与等价 DSL（见[第 5 节](#5-单向编译)），不做反向恢复。
- **在线测试**：编辑器可对当前 UI 树发起试运行，编译并在内核执行，回传递归执行详情（`RuleResult` 树）。
- **执行路径渲染**：试运行后，画布高亮实际走过的执行路径，条件未命中的分支、并行各分支、循环轮次都能在同一棵递归树上直观呈现，编辑视图与执行视图共用一套结构。

## 2. 职责边界

`mosika-ui` 提供可序列化、可递归遍历的 UI AST，以及 UI AST 到内核 `RuleNode` 的单向编译；不包含页面、布局和 Web 依赖。

`mosika-web` 是参考控制面，负责命名空间、原子规则、JavaScript UDF、业务场景、版本和 UI AST 的管理，并提供 REST、SQLite 持久化与静态页面。Spring 扫描得到的 Java UDF 会合并到查询和运行时套件中，但不进入数据库，也不能通过控制面修改。

UI AST 及其 JSON 是编辑和持久化的事实来源。执行树只保留运行语义，不能从 `RuleNode` 或 DSL 反向恢复 UI 布局和编辑元数据。

## 3. 模型结构

模型把类型识别、节点命名、执行拓扑和规则表达式分层：

```text
TypeNode
└─ NameNode(name)
   ├─ TreeNode(next)
   ├─ UINode
   │  ├─ FlowNode<T extends RuleNode>(rule, next)
   │  │  ├─ ActionNode<AtomicNode>
   │  │  ├─ ConditionNode<BooleanNode>
   │  │  └─ LoopNode<BooleanNode>(max)
   │  └─ BranchNode<T extends UINode>(branches)
   │     ├─ DecisionNode<ConditionNode>(defaultBranch)
   │     ├─ SerialNode<UINode>
   │     └─ ParallelNode<UINode>
   └─ RuleNode
      └─ AtomicNode(expr, args)
         └─ BooleanNode(negative)
            └─ LogicNode(rules)
               └─ MatchNode(minHits, maxHits)
```

## 4. 节点与字段

| JSON 类型 | Java 节点 | 自有递归边 | 语义 |
| --- | --- | --- | --- |
| `TreeNode` | `TreeNode` | `next` | 序列化、遍历、校验和编译入口 |
| `ActionNode` | `ActionNode` | `rule`、`next` | 执行动作规则，再执行可选后继 |
| `ConditionNode` | `ConditionNode` | `rule`、`next` | 判断条件规则，命中后执行可选流程 |
| `SerialNode` | `SerialNode` | `branches` | 按顺序执行完整流程子树 |
| `ParallelNode` | `ParallelNode` | `branches` | 并发执行完整流程子树并等待完成 |
| `DecisionNode` | `DecisionNode` | `branches`、`defaultBranch` | 有序检查条件分支，命中首个后停止 |
| `LoopNode` | `LoopNode` | `rule`、`next` | 条件命中时重复执行循环体，最多执行 `max` 轮 |
| `AtomicNode` | `AtomicNode` | 无 | 规则引用，可携带模板参数 |
| `BooleanNode` | `BooleanNode` | 无 | 可整体取反的规则引用 |
| `LogicNode` | `LogicNode` | `rules` | 与或组合 |
| `MatchNode` | `MatchNode` | `rules` | `some` 限定匹配组合 |

字段归属：

| 字段 | 所属类型 | 含义 |
| --- | --- | --- |
| `name` | `NameNode` | 展示名称，不参与编译和求值 |
| `rule` | `FlowNode` | 当前单分支节点绑定的规则表达式 |
| `next` | `FlowNode`、`TreeNode` | 单出口关系，具体语义由节点类型决定 |
| `branches` | `BranchNode` | 有序的完整流程子树 |
| `defaultBranch` | `DecisionNode` | 条件均未命中时执行的默认流程 |
| `max` | `LoopNode` | 最大循环次数 |
| `expr`、`args` | `AtomicNode` | 规则引用和模板参数 |
| `negative` | `BooleanNode` | 是否对整个规则表达式取反 |
| `rules` | `LogicNode` | 有序子规则列表 |
| `minHits`、`maxHits` | `MatchNode` | 匹配数量范围 |

`BranchNode` 不拥有 `rule` 或 `next`。组合结构需要与后续子树串联时，由外层 `SerialNode` 表达。

`ConditionNode` 与 `LoopNode` 的 `rule` 都是 `BooleanNode`：条件节点的判断条件、循环节点的循环条件复用同一套规则子树模型。`LogicNode` 和 `MatchNode` 通过继承复用可取反语义，但不使用继承得到的原子调用参数；模板参数只由叶子 `AtomicNode`、`BooleanNode` 生成到规则 DSL 中。

## 5. 遍历与校验

`TreeNode.visit()` 按以下关系遍历执行树及其嵌入的规则树：

```text
TreeNode    -> next
FlowNode    -> rule, next
BranchNode  -> branches
DecisionNode -> branches, defaultBranch
LogicNode   -> rules
```

`TreeNode.validate()`（`TreeVisitor.NODE_VALIDATOR`）执行结构校验：

- `TreeNode.next` 和每个 `FlowNode.rule` 必须存在
- `SerialNode`、`ParallelNode` 至少包含一个分支（参考 Web 编辑器要求至少两个）
- `DecisionNode` 至少包含一个条件分支，且条件分支与默认分支合计至少形成两个结果出口
- `DecisionNode.defaultBranch` 只能是 `ActionNode`、`DecisionNode`、`LoopNode`、`ParallelNode` 或 `SerialNode`
- `LoopNode.max` 不能为负数，`rule` 和 `next` 必须存在
- `LogicNode.expr` 只能是 `&&` 或 `||`，并且至少包含两个子规则
- `MatchNode` 至少包含一个子规则，上下界不能同时为空，并满足 `0 <= min <= max <= rules.size()`
- 叶子规则表达式不能为空

`TreeNode.validateSize(maxDepth, maxNodes)` 用对象身份检查整棵树，拒绝重复对象引用和循环引用。参考 Web 在服务端和编辑器中使用相同预算：

```text
最大深度  128
节点总数  2000
```

参考 Web 在保存、测试和发布前都执行结构完整性校验，必需递归关系未补全（画布上表现为虚拟插槽）时不提交；服务端在发布时继续执行完整结构校验、编译和引用校验。

## 6. 单向编译

```text
UI TreeNode JSON
      │ deserialize / validateSize
      ▼
   TreeNode
      │ validate / UINodeAdapter.toRule()
      ▼
   RuleNode
      │ expr / RuleDefinition(ruleType=2)
      ▼
   RuleSuite
```

`UINodeAdapter.toRule()` 的映射：

| UI 结构 | 内核结构 |
| --- | --- |
| 单个 `ActionNode` | 解析 `rule.ruleExpr()` |
| 连续 `ActionNode.next` | 一个 `SerNode` |
| 无后继的 `ConditionNode` | 条件规则自身 |
| 有后继的 `ConditionNode` | `CaseNode(condition, matched)` |
| `DecisionNode` | 按条件顺序反向嵌套 `CaseNode` |
| `SerialNode` | 带 `∅` 结构占位的 `SerNode` |
| `ParallelNode` | 带 `∅` 结构占位的 `ParNode` |
| `LoopNode` | 内核 `LoopNode(max, condition, action)` |

编译只读取执行语义：

- `name`、选择状态、折叠状态和节点坐标不进入执行树
- `AtomicNode.expr` 保存稳定规则 ID，不复制后台 JavaScript 表达式
- `DecisionNode` 按列表顺序检查条件，条件没有命中流程时以 `∅` 表示命中后停止
- 业务场景引用以 `f<id>` 存在普通动作规则引用中，不引入专用调用节点
- 不提供从执行树返回 UI AST 的逆向转换

## 7. 画布与规则弹窗

主画布只展开 Flow 递归：

- `SerialNode`、`ParallelNode`、`DecisionNode`、`LoopNode` 分别显示为「串」「并」「分」「循」等结构节点
- `ConditionNode` 与其规则子树合并为一个条件节点，命中流程沿 `ConditionNode.next` 在主画布继续展开
- 循环条件复用完整规则弹窗，循环体与串行、并行分支一样支持任意流程节点
- 节点位置、折叠、缩放和连线方向只服务阅读
- 主画布和规则弹窗只允许同一父节点、同一有序列表中的兄弟重排

节点交互由一份集中的节点能力定义驱动（画布、右栏属性和右键菜单读取同一份定义）：

- 每类节点由「自身配置 + 递归关系」组成；创建时先补全自身配置，未补全的必需递归关系在画布上显示为虚拟插槽
- 虚拟插槽只由视图层生成，不进入 UI AST，不参与序列化，也不计入节点数量
- 双击动作节点打开动作配置，双击条件 / 循环节点打开规则弹窗；结构节点通过属性栏或右键菜单添加子节点
- 串行与并行可互相转换，其他结构变化通过插入节点完成
- 动作、条件、循环等单分支直通节点存在合法后续时，可选择仅删除当前节点并把后续提升到当前位置；串行、并行、分支等多分支节点只支持删除整棵子树

双击条件节点或点击「查看规则」打开规则弹窗：

- 弹窗只编辑纯 Rule 子树，不导航 `ConditionNode.next`
- 一条引用使用原子条件，多条引用可组合为与或
- 原子条件支持模板参数和取反
- 条件与、条件或、限定匹配可互相转换，并共享子规则的新增、排序、删除与类型转换操作
- 「保存」提交当前规则子树，「取消」或 Esc 恢复打开弹窗时的快照

所有节点的可选展示名称统一使用 `name`。条件画布名称来自 `ConditionNode.name`，内部规则名称来自 `ConditionNode.rule.name`，两者互不覆盖。

## 8. 引用、版本与发布

参考 Web 在发布时校验引用：

- 动作节点只能引用动作类型原子规则、已发布业务场景或内置 `∅`
- 条件节点只能引用条件类型原子规则或允许的内置条件
- 业务引用必须存在、可用并与当前场景属于同一命名空间

每个业务场景拥有稳定 `flowId` 和递增版本：

- 新建场景生成版本 1 的草稿
- 草稿只能保存完整结构（必需递归关系与自身配置补全后才可提交）
- 发布执行严格树编译和引用校验
- 发布成功后，原当前发布版本转为历史版本，新版本成为当前发布版本
- 发布、历史和停用版本只读；修改只读版本时，先以选定版本为基础创建新草稿
- 发布或保存失败时不部分替换当前树

发布流程在事务提交前构造候选 `RuleSuite`，提交后替换当前命名空间的运行套件。Core 本身不保存草稿、版本和发布状态。

## 9. 页面入口

- `/`：产品首页
- `/namespaces`：命名空间选择与管理
- `/scenes`：业务场景与版本
- `/rules`：原子规则库
- `/udfs`：Java 与 JavaScript UDF 注册中心，其中 Java UDF 只读展示实现类和暴露方法详情
- `/flow/{flowId}`：指定业务场景的规则树编辑器

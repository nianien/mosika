## 1. 文档目的

本文描述 `mosika-core` 的设计构思、语义边界和运行机制，重点回答以下问题：

- Mosika 为什么同时存在规则 DSL 和 JavaScript 表达式；
- `RuleNode` 为什么既能表示逻辑规则，又能表示串行、并行和条件执行；
- `EvalResult.matched` 与 `EvalResult.result` 为什么必须分离；
- `$`、`$$`、`$args`、规则描述和 UDF 如何构成一套完整的表达式执行环境；
- 模板参数化规则如何让同一个 `ruleId` 在一棵规则树中按节点独立绑定和执行；
- UDF 为什么需要分组、`UdfDelegate` 和 ByteBuddy 动态类；
- `RuleSuite`、原子/复合 `RuleDefinition` 与命名规则递归引用如何组成运行时套件；
- 并发执行、缓存、执行详情和套件发布分别在哪一层处理。

本文只讨论内核，不讨论 UI AST、页面布局、Web API、持久化和产品层 Flow。Core 不定义 Flow 类型或 Flow 专用 API。

本文采用三类证据解释设计：当前源码用于确认真实调用链，核心测试用于确认可观察契约，Git 历史用于区分长期设计与近期升级。只有三者能够相互印证的内容才作为确定设计；仅由代码形态推测的可能性不作为缺陷或设计结论。

## 2. 一句话架构

Mosika Core 是一个以 `RuleNode` 递归树为执行模型、以规则 ID DSL 为结构语言、以 JavaScript 为业务表达式语言、以 UDF 为扩展机制、以 `RuleSuite` 为发布单元的通用规则引擎。

它不是把所有能力塞进一种语言，而是有意拆成两个层次：

```text
结构层：规则 ID DSL
    负责 与、或、非、命中数、条件、串行、并行及其作用域

计算层：JavaScript 表达式
    负责读取业务对象、调用 Java/UDF、计算和返回业务值
```

结构层决定“执行哪些规则以及如何组合”，计算层决定“每条原子规则具体做什么”。

## 3. 设计目标与基本原则

### 3.1 规则定义与规则编排分离

`RuleDefinition` 定义一条可独立执行的规则：

```text
ruleId      稳定标识
expression  JavaScript 业务表达式，或 useType=2 时的规则 ID DSL
desc        可执行的规则描述
useType     0 表示原子规则，2 表示复合规则
```

复合规则 DSL 不复制业务表达式，只引用 `ruleId`：

```text
isAdult && isVerified ? grant : reject
```

这样可以独立维护业务规则和执行结构，也使复合规则和详情追踪都能使用稳定规则标识。

### 3.2 树是执行语义，不是展示结果

Mosika 使用递归树表达控制作用域，不使用通用 DAG：

```text
S(
  P(a, b),
  P(c, d)
)
```

该结构明确表示：先并行执行 `a、b` 并等待完成，再并行执行 `c、d`。并行子树的结束就是局部作用域的自然汇合，不需要多入边、隐式汇合点或额外图算法。

### 3.3 匹配状态与业务结果分离

任意节点都可能同时具备两个维度：

- 它作为条件时是否命中；
- 它实际产生了什么业务值。

因此 `EvalResult` 同时保存：

```text
matched  逻辑或控制状态
result   业务返回值
```

二者不能互相替代。逻辑节点主要解释 `matched`，动作和条件分支可能传递 `result`，串并行结构则只表示执行完成。

### 3.4 规则作者处于可信执行边界

规则表达式不是面向不可信用户的安全模板，而是可执行 JavaScript。设计上允许：

- 访问 Java 对象属性和方法；
- 使用 `Java.type(...)`；
- 传递和返回 `BigDecimal` 等 Java 类型；
- 调用 Java UDF 和 JavaScript UDF；
- 通过 `$$` 读取、写入本次规则上下文。

因此 GraalJS 的 Java 互操作能力是产品能力，不是默认需要消除的暴露面。若调用方需要不可信脚本隔离，应在内核外建立另一套授权和运行边界，不能通过缩减现有表达式语义实现。

### 3.5 编译配置与单次执行状态分离

规则和 UDF 在 `RuleSuite` 构造阶段完成装配；一次实际求值则创建独立的 `RuleVisitor` 和 JavaScript Context。

这形成两类生命周期：

```text
套件生命周期：RuleSuite / RuleEngine / 编译 Source / UDF 对象图
请求生命周期：RuleVisitor / RuleContext / EvalNode 详情树 / JS Context
```

## 4. 总体分层

```text
RuleLoader
  ├─ RuleDefinition[]
  └─ UdfDefinition[]
          │
          ▼
RuleSuite 构建与编译
  ├─ RuleEngine
  │    ├─ JavaScript Source 缓存
  │    ├─ 唯一规则注册表
  │    └─ 编译后的 UDF 命名空间
  └─ NodeBuilder
       ├─ 套件专属 NodeGenerator
       └─ 命名 RuleNode 缓存
          │
          ▼
evalRule / evalExpr
          │
          ▼

          │
          ├─ ExprNode ──> RuleEngine ──> GraalJS

```

## 5. 两层表达式语言

### 5.1 外层：规则 ID DSL

ANTLR 语法位于 `src/main/antlr4/Rule.g4`。DSL 的原子项是规则 ID，组合能力包括：

| 语法 | 节点 | 含义 |
| --- | --- | --- |
| `!a` | `NotNode` | 对规则命中状态取反 |
| `a&&b` | `AndNode` | 逻辑与，遇到未命中即短路 |
| `a||b` | `OrNode` | 逻辑或，遇到命中即短路 |
| `a?b:c` | `CaseNode` | 根据 `a` 选择一个执行分支 |
| `a?b` | `CaseNode` | 仅有命中分支的条件执行 |
| `a->b` | `SerNode` | 串行执行结构 |
| `a=>b` | `ParNode` | 并行执行结构 |
| `hits(2,_,a,b,c)` | `HitsNode` | 至少命中两个子规则 |
| `a("""{"limit":100}""")` | `ExprNode` | 为当前规则节点绑定 JSON 模板参数 |
| `_` | 命中边界 | 该侧不限制 |
| `∅` | 结构占位规则 | 稳定串并行结构，不参与业务计算 |

括号决定显式作用域。解析后不再依赖文本位置，而是由 `RuleNode` 类型和父子关系承载语义。

### 5.2 内层：JavaScript 业务表达式

每个普通 `RuleDefinition` 的 `expression` 是 JavaScript，例如：

```javascript
isAdult($.name, $.age, $$)
```

模板参数化规则还可以读取当前节点的 `$args`：

```javascript
$.input > $args.limit
```

或者：

```javascript
$.amount.add(new (Java.type('java.math.BigDecimal'))('1.00'))
```

动作规则可以直接返回对象字面量：

```javascript
{stage: "CLAIM_EXTRACTION", status: "completed", claimCount: $.claimCount}
```

`RuleEngine` 会在编译边界自动为顶层对象字面量补充分组括号，规则作者不需要为避免对象被解析为代码块而手工书写 `({...})`。其他 JavaScript 表达式保持原样编译。

其中：

| 名称 | 含义 |
| --- | --- |
| `$` | 本次规则求值的业务对象，即 `RuleVisitor.data` |
| `$$` | 本次执行的规则上下文，即 `RuleVisitor` 本身 |
| `$args` | 当前原子规则节点绑定的模板参数对象，未传参数时为空对象 |
| 顶层 UDF 名称 | `UdfContainer` 编译后放入 JS bindings 的 UDF 或分组对象 |

`$`、`$$` 和 `$args` 具有明显的表达式符号特征，不容易与普通业务字段冲突；同时保持规则文本紧凑。

### 5.3 模板参数化规则

只有阈值不同的业务判断不应该复制成多条规则：

```text
r1 = $.input > 100
r2 = $.input > 200
r3 = $.input > 300
```

Mosika 允许把规则定义为模板：

```text
threshold = $.input > $args.limit
```

再由 DSL 中的每个规则节点绑定自己的 JSON 参数：

```text
threshold("""{"limit":100}""") || threshold("""{"limit":300}""")
```

ANTLR4 只识别三引号参数块的边界，`DefaultRuleVisitor` 将原始参数交给 `ExprNode`，再由 `JsonUtils` 解析为 `Map<String,Object>`。外层 DSL 不需要实现 JSON 文法，也不会把参数文本替换进 JavaScript 源码。

规则的 JavaScript `Source` 继续按定义预编译；执行当前 `ExprNode` 时，`RuleVisitor` 把该节点的参数传给 `RuleEngine`，由新建的 GraalJS `Context` 绑定为 `$args`。同一规则可以在一棵树中带不同参数多次出现，而不需要重新编译规则脚本。

`RuleArguments` 在 `ExprNode` 构造时一次性保存参数的规范化 JSON 字符串和字段有序的 `Map<String,Object>`。参数化调用按规则 ID 和规范化 JSON 字符串组成的不可变键复用叶子结果，执行时直接使用解析结果绑定 `$args`，不再重复解析或规范化。对象字段在所有嵌套层级递归排序，数组元素顺序保留。同一参数组合在一次顶层执行中只真正求值一次，不同参数组合分别求值；每次出现仍生成独立 `EvalNode` 并保存结果。无参数调用保持按 `ruleId` 缓存的既有语义，且 `$args` 绑定为空对象。

模板参数的完整语法、缓存和边界见[模板参数化规则](./模板参数化规则.md)。

### 5.4 为什么不把两层语言合并

如果直接在流程 DSL 中嵌入完整业务 JavaScript，会产生三个问题：

1. 结构解析器必须理解 JavaScript 的字符串、正则、对象字面量和运算符；
2. UI、持久化和规则复用无法稳定引用原子规则；
3. 执行详情难以用业务规则 ID 归档和解释。

当前设计让 DSL 只解析有限、稳定的组合语法，把复杂计算交给成熟的 JavaScript 引擎。

## 6. 规则描述也是可执行表达式

`RuleDefinition.desc` 不是静态注释。它是使用同一份 `$`、`$$`、`$args` 执行的简化规则表达式，主要用于生成可解释的执行详情。

示例：

```java
new RuleDefinition(
    "101",
    "isAdult($.name,$.age,$$)",
    "${$.name}的年龄(${$.age})小于${$$.minAge}岁"
)
```

执行顺序为：

```text
1. 执行规则 expression
2. UDF 可通过 $$ 写入 minAge 等上下文属性
3. RuleVisitor 构造执行详情
4. 使用当前 $ 和 $$ 执行 desc
5. 生成 RuleResult.desc
```

因此描述能够引用规则执行过程中写入的上下文，而不需要把诊断字段塞进业务 `result`。

当前描述采用标准 JavaScript 模板插值：

```text
${$.name}
${$$.agent}
${$args.minAge}
${$.name.toUpperCase()}
```

`compileDesc()` 使用 `String.raw` 模板字符串编译为 GraalJS `Source`，既保留静态文本中的反斜杠和换行，又让 `${...}` 内保持完整 JavaScript 语义，包括方法调用、对象字面量和正则表达式。

该语法替代了旧的 `{$.a}` 自定义正则拆分方式。它是明确的语法升级边界；仓库外持久化的旧描述需要与代码同步迁移。

## 7. `RuleNode`：统一递归执行模型

### 7.1 统一接口

所有节点实现：

```java
EvalResult eval(RuleContext context);
String expr();
```

同时通过默认组合方法形成节点代数：

```java
and(node)
or(node)
not()
next(node)
```

组合操作返回新的 `RuleNode`，因此规则可以用解析器构建，也可以由 Java/UI AST 直接构建。

### 7.2 节点分类

| 类别 | 节点 | 核心职责 |
| --- | --- | --- |
| 原子规则 | `ExprNode` | 根据规则 ID 调用 `RuleContext.eval()` |
| 复合规则引用 | `CompositeNode` | 为命名复合规则包裹展开后的内部规则树 |
| 逻辑节点 | `AndNode`、`OrNode`、`NotNode`、`HitsNode` | 解释子节点 `matched` |
| 条件节点 | `CaseNode` | 选择并执行一个分支 |
| 执行结构 | `SerNode`、`ParNode` | 控制所有子节点的执行顺序 |

这种统一接口并不意味着所有节点具有相同语义。节点类型本身就是语义来源。

### 7.3 逻辑节点

#### `AndNode`

按顺序访问子节点：

- 任一子节点 `matched=false`，立即返回未命中；
- 全部命中，返回命中；
- 返回值表达逻辑判断，不透传某个子节点的业务 `result`。

#### `OrNode`

按顺序访问子节点：

- 任一子节点 `matched=true`，立即返回命中；
- 全部未命中，返回未命中。

#### `NotNode`

访问子节点并反转其 `matched`。连续两次 `not()` 会回到原节点。

#### `HitsNode`

统计子节点命中数是否落在 `[minHits, maxHits]` 区间：

- `null` 边界对应 DSL 中的 `_`；
- 两侧不能同时不设限；
- 最大命中数不能超过规则数；
- 当最小值已经保证、最大值也不可能超出时提前返回命中；
- 当最大值已超出，或剩余节点不可能达到最小值时提前返回未命中。

`HitsNode` 使用 `context.visit(node)`，因此短路和详情树保持一致。

### 7.4 条件节点 `CaseNode`

`CaseNode` 先访问条件节点，只执行被选择的分支：

```text
condition=true  -> trueCase
condition=false -> falseCase
```

如果分支存在，`CaseNode` 传递该分支的 `result` 和 `matched`；如果没有对应分支，则返回 `result=null, matched=false`。

这使条件节点既可以做纯判断，也可以承载动作和更复杂的流程子树。

### 7.5 串行结构 `SerNode`

`SerNode`：

- 按声明顺序访问所有非 `∅` 子节点；
- 不因为某个子节点未命中而停止；
- 不使用最后一个子节点结果代表整个串行结构；
- 正常完成统一返回 `result=null, matched=true`；
- 子节点异常继续向上传播。

串行结构表达的是“这些步骤都执行完成”，而不是逻辑与。

### 7.6 并行结构 `ParNode`

`ParNode`：

- 使用公共执行池并发访问所有非 `∅` 分支；
- 等待全部分支完成；
- 不把子分支命中状态聚合为真假；
- 正常完成统一返回 `result=null, matched=true`；
- 子分支异常由 `CompletableFuture` 汇集，对外抛出时解包并保留原始业务异常；
- 等待被中断时恢复当前线程的中断标记，并使用 `RuleEvalException` 表达结构执行失败；
- 等待超时或被中断时取消尚未开始执行的分支，不强制终止已在运行的分支；
- 当前实现等待上限为一分钟。

并行结构表达的是“这些分支并发执行并在本层汇合”，而不是逻辑或。

### 7.7 `next()` 的协变追加语义

`RuleNode.next()` 默认创建 `SerNode`，但组合节点重写为自身追加：

```text
SerNode.next(x) -> 在串行列表末尾追加 x
ParNode.next(x) -> 在并行列表末尾追加 x
```

因此不能只根据方法名把 `ParNode.next()` 理解成“创建后续串行步骤”。它在 `ParNode` 上表示继续扩展当前并行组合。

当一个流程需要以并行结构开头、之后再进入串行步骤时，可以使用结构标记稳定外层串行根：

```text
∅->(a=>b)->c
```

解析结果是：

```text
SerNode(
  ∅,
  ParNode(a,b),
  c
)
```

### 7.8 不可变 AST 与缓存安全

当前组合节点使用 `List.copyOf(...)` 保存子节点；追加操作创建新节点而不是修改旧节点。

这样做是因为同一套件会缓存解析后的 `RuleNode`。如果调用方在组合时修改共享节点，后续执行会被静默污染。不可变结构使缓存、并发执行和 UI 到内核的单向编译可以共享同一套节点语义。

## 8. 解析与复合规则

### 8.1 ANTLR 解析链路

```text
DSL 文本
  -> RuleLexer / RuleParser
  -> DefaultRuleVisitor
  -> NodeGenerator
  -> RuleNode 树
```

`Antlr4Parser` 负责配置统一错误监听器；解析失败后由 `NodeBuilder` 包装成 `RuleParseException`，同时发送解析事件。

### 8.2 `NodeBuilder` 与 `RuleSuite` 的职责

`NodeBuilder.build(expr)` 是通用解析入口。它只缓存普通命名规则和构造阶段递归编译的命名复合规则，任意临时 DSL 组合的根节点每次重新解析。

套件运行路径由 `RuleSuite` 组合 `RuleEngine` 和 `NodeBuilder`：

- 每个 `RuleSuite` 持有自己的 `NodeBuilder`；
- 每个 `NodeBuilder` 持有套件专属的 `NodeGenerator` 和命名节点缓存；
- 完整临时 DSL 不缓存，因此 `RuleSuite` 可以安全执行任意节点组合；
- 命名复合规则在套件构造阶段递归预编译，顶层构建与递归引用共享同一个 `CompositeNode`；
- `NodeGenerator` 不维护规则注册表，也不复制 `RuleEngine` 的注册状态；
- 不同套件的复合规则定义不会污染彼此。

因此解析配置属于套件，而不是进程全局状态。

### 8.3 复合规则展开

`useType=2` 的 `RuleDefinition` 表示命名复合规则。它的 `expression` 不是 JavaScript，而是另一段规则 ID DSL。

`NodeGenerator.create(compositeRules)` 在遇到复合规则 ID 时：

1. 创建 `CompositeNode` 保留外层规则 ID；
2. 递归解析其内部 DSL；
3. 使用栈记录当前解析路径；
4. 遇到循环引用时立即失败；
5. 缓存编译结果，后续顶层编译或其他复合规则引用直接复用。

复合规则内部直接使用裸 `ruleId` 引用其他命名规则：该 ID 存在于复合规则表时继续展开为 `CompositeNode`，否则生成 `ExprNode` 并在执行时交给 `RuleEngine` 解析。`NodeGenerator` 不需要 `registeredRules` 一类额外参数，因为内置规则和全部业务 `RuleDefinition` 已由 `RuleEngine` 统一注册；再维护一份注册集合会复制状态并产生不一致风险。两者不使用不同语法或执行入口，目标子树和执行详情完整保留。直接和间接循环引用都由同一个递归解析栈在编译阶段拒绝。

三者的职责边界为：

| 组件 | 职责 |
| --- | --- |
| `RuleEngine` | 注册全部规则，预编译原子 JavaScript，按 `ruleId` 执行叶子规则 |
| `NodeGenerator` | 根据完整复合规则表构造 AST，递归展开 `CompositeNode` 并检测循环 |
| `RuleSuite` | 组装 `RuleEngine` 和套件专属 `NodeGenerator`，建立顶层规则索引 |

例如：

```text
a = 1 || b
b = 2 && 3
```

会形成：

```text
CompositeNode(a,
  Or(
    Expr(1),
    CompositeNode(b, And(Expr(2), Expr(3)))
  )
)
```

命名复合规则既保留可解释的外层身份，又拥有可递归追踪的内部详情。

## 9. `RuleVisitor`：单次执行的核心上下文

每次 `RuleSuite.eval(...)` 创建新的 `RuleVisitor`。它同时承担四个角色：

```text
RuleContext     节点递归访问接口
UdfContext      UDF 可访问的规则上下文
Map             $$ 暴露的可读写属性容器
Trace Builder   EvalNode 执行详情树构造器
```

### 9.1 叶子规则缓存与参数化调用

无参数 `ExprNode.eval()` 最终调用 `context.eval(ruleId)`。`RuleVisitor` 使用 `evalCache.computeIfAbsent(...)` 保证同一无参数规则 ID 在一次执行中只真正求值一次。

这有两个作用：

- 避免同一原子规则在复合表达式中重复执行；
- 避免有副作用的规则或 UDF 在同一次执行中被重复触发。

参数化节点调用 `context.eval(ruleId, arguments)`，并使用规则 ID 和规范化 JSON 字符串组成不可变缓存键：

```text
r1("""{"limit":100}""") || r1("""{"limit":300}""")
```

两次 `r1` 的参数不同，因此分别求值并拥有独立结果和动态描述。参数内容相同时复用评估结果，但每次节点访问仍创建独立 `EvalNode`，执行详情不会合并。

非叶子节点的结果不写入 `evalCache`。无参数叶子使用规则 ID、参数化叶子使用规则 ID 和结构化参数作为缓存键。每次 `visit()` 创建的 `EvalNode` 直接保存当前路径上的 `EvalResult`，详情组装不再依赖缓存键反查结果。

### 9.2 当前规则

进入 `ExprNode` 时，`currentRule` 写入基础规则 ID，不包含参数文本。UDF 可以通过 `UdfContext.getRule()` 获知是谁调用了自己。

`currentRule` 使用 `ThreadLocal`，使并行分支分别维护自己的当前规则。

### 9.3 共享业务上下文 `$$`

`RuleVisitor` 继承 `LinkedHashMap<String,Object>`，并实现：

```text
getProperty
setProperty
removeProperty
```

JavaScript 规则通过 `$$.property` 访问，Java UDF 通过 `UdfContext` 访问。并行写入方法使用同步保护；并行分支共享同一份本次执行上下文。

`$args` 不存入该共享 Map。它由当前 `ExprNode` 单独持有并在执行规则和描述时显式传递，因此一个节点的参数不会覆盖另一个节点的参数。

### 9.4 执行详情树

每次 `visit(node)` 都创建 `EvalNode` 并挂到当前父节点。非叶子节点进入时更新 `currentEval`，退出时在 `finally` 中回溯。

`finally` 回溯保证异常路径不会把后续节点挂到错误父节点。

并行执行时，每个子线程先恢复并行节点对应的父执行节点，再访问自己的分支。`EvalNode.children` 使用线程安全集合保存并行分支详情。

### 9.5 详情物化

执行结束后，`getRuleResults()` 将 `EvalNode` 树转换为 `RuleResult` 树：

- 从每个 `EvalNode` 直接读取该次执行的节点结果；
- 对原子规则和命名复合规则求值描述，渲染期间将 `currentRule` 限定为正在物化的规则 ID，把同一节点参数绑定为 `$args`，并在结束后恢复原值；
- 递归附加 `subRules`；
- 保留真实短路后的访问路径，而不是静态 AST 全量展开。

因此详情表达“本次实际执行了什么”，而不是“理论上可能执行什么”。

## 10. 结果模型

### 10.1 `EvalResult`

字段：

| 字段 | 含义 |
| --- | --- |
| `expr` | 当前节点或规则表达式 |
| `result` | 业务返回值 |
| `matched` | 作为条件时的命中状态 |

普通 JavaScript 返回值通过默认规则转换为 `matched`：

| 返回值 | 命中规则 |
| --- | --- |
| `null` | 未命中 |
| `Boolean` | 使用原值 |
| `Number` | 大于零时命中 |
| `String` | `no/false/null/0/fail` 视为未命中，其余命中 |
| `Collection` | 非空时命中 |
| `Map` | 非空时命中 |
| 其他对象 | 命中 |

数字判定按具体数值类型精确比较：`BigDecimal` 和 `BigInteger` 使用 `signum()`，整数类型使用 `longValue()`，其他数字使用 `doubleValue()`，避免把任意 `Number` 统一缩窄后再判定。

结构节点和部分逻辑节点可以使用显式构造函数分别指定 `result` 与 `matched`，不必依赖默认转换。

### 10.2 `RuleResult`

`RuleResult` 继承 `EvalResult`，增加：

```text
desc      动态规则描述
subRules  实际执行的子规则详情
```

它属于可解释性模型，不改变业务返回值。

### 10.3 `NodeResult`

`NodeResult` 是 `RuleSuite` 对外返回模型：

```text
expr     根节点 DSL
result   根节点业务结果
details  执行详情
```

带外部上下文的求值入口可以关闭详情构造，并在执行后把 `RuleVisitor` 属性写回调用方提供的 Map。

### 10.4 `NaResult`

`NaResult` 是区别于 Java `null` 的“无业务结果”哨兵。内置 `null` 和 `∅` 规则返回该对象。

`RuleSuite` 发现根节点结果本身是 `NodeResult` 时直接返回，使 `NaResult` 这类哨兵能够穿过普通 `EvalResult` 包装。

## 11. `RuleEngine`：JavaScript 规则执行器

### 11.1 构造阶段

一个 `RuleSuite` 创建一个 `RuleEngine`。构造过程：

1. 注册内置规则 `true`、`false`、`null`、`∅`；
2. 把全部业务 `RuleDefinition` 注册到唯一规则定义表；
3. `useType=0` 的原子规则按表达式语义自动包装并预解析 JavaScript `Source`；
4. 复合规则跳过 JavaScript 编译，由外层 DSL 解析器处理；
5. 所有规则描述预编译；
6. `UdfContainer` 构建完整 UDF 命名空间对象。

因此 `RuleEngine` 已经同时承担规则注册和原子表达式编译，不需要 `NodeGenerator` 再接收一份规则 ID 集合。JavaScript 语法错误会在套件构造阶段暴露；普通 `ExprNode` 的 ID 查找仍由执行阶段的 `RuleEngine.evalRule()` 完成。

### 11.2 执行阶段

每次 `evalRule()` 或 `evalExpr()`：

1. 创建新的 GraalJS `Context`；
2. 绑定 `$`；
3. 绑定 `$$`；
4. 绑定所有顶层 UDF；
5. 绑定当前节点参数 `$args`，无参数时使用空对象；
6. 执行缓存的 `Source`；
7. 把 Polyglot `Value` 转换为脱离 Context 生命周期的 Java 值；
8. 关闭本次 Context。

这保证普通规则执行之间不共享 JavaScript 可变全局状态，同时允许复用编译结果。

### 11.3 编译缓存

`RuleEngine` 维护两套并发缓存：

```text
compiledScripts  key=JavaScript expression
compiledDesc     key=description text
```

缓存值是可跨 Context 使用的 GraalJS `Source`，而不是绑定到某个 Context 的函数对象。

### 11.4 GraalJS 运行时

`JsRuntime` 维护进程级共享 `Engine`。所有普通规则 Context 使用该 Engine，以复用 GraalJS 的解析和编译基础设施。

Context 配置保留：

```text
HostAccess.ALL
任意 Java 类查找
Nashorn compatibility
ECMAScript latest
```

`ECMAScript latest` 与 Nashorn 兼容模式同时设置，是为了在保持旧 Java 互操作能力的同时支持模板字符串等现代语法。

### 11.5 Polyglot 结果转换

`JsRuntime.toJava()` 的目标不是把 Context 继续暴露给调用方，而是在 Context 关闭前转换结果：

```text
Host Object -> 原 Java 对象
Boolean     -> Boolean
String      -> String
Number      -> Integer / Long / Double
Array       -> ArrayList
Members     -> LinkedHashMap
```

先判断 `isHostObject()`，因此 Java 传入并原样返回的 `BigDecimal` 等类型不会被强制降级成 JavaScript 数字。

## 12. UDF 设计

### 12.1 `UdfDefinition` 是统一声明模型

```text
group  可选分组路径，例如 content.generation
name   UDF 名称，例如 eval
udf    Java 对象或 JavaScript 源码字符串
```

它不区分 Java UDF 和 JS UDF 的外部注册方式。类型差异由 `UdfContainer` 在装配阶段处理。

### 12.2 UDF 分组

分组使用点号形成多级命名空间：

```java
new UdfDefinition("policy.sys", "replace", udf)
```

规则中调用：

```javascript
policy.sys.replace($)
```

注册时，`UdfContainer` 把分组拆成嵌套 Map：

```text
policy
  └─ sys
      └─ replace
```

同名 UDF 可以存在于不同分组；同一分组内名称必须唯一。一个路径位置不能同时既是函数又是子分组。

### 12.3 为什么使用 ByteBuddy

GraalJS 表达式需要用自然属性语法访问分组：

```javascript
policy.sys.replace(...)
```

普通 Map 在不同 JavaScript 引擎和 Java 互操作模式下不一定等价于稳定的 Java 属性对象。`UdfContainer.compileUdf()` 使用 ByteBuddy 递归生成具有公共字段的动态类：

```text
UDF$Policy
  public Object sys

UDF$Policy$Sys
  public Object replace
```

字段值再通过 `MethodHandle` 写入。最终每个顶层分组都是一个真实 Java 对象，GraalJS 可以沿字段自然访问。

ByteBuddy 因此承担的是“动态命名空间对象编译”，不是 Java UDF 方法代理；移除它会改变分组对象的 JavaScript 属性语义。

### 12.4 `UdfDelegate`

所有叶子 UDF 最终由 `UdfDelegate.Wrapper` 包装。它负责：

- 查找名为 `apply` 且参数数量匹配的方法；
- 忽略编译器生成的 bridge method；
- 根据目标泛型参数类型转换 JavaScript 参数；
- 支持一个 UDF 实现多个不同参数数量的函数接口；
- 当 UDF 作为另一个 UDF 的参数传入时，解开 Wrapper，传递真实函数对象；
- 对 `JsUdf` 的可变参数调用做适配。

因此 Java UDF 可以同时支持：

```java
apply(User user)
apply(User user, String name)
```

也可以接收 `List<T>`、`Map<K,V>`、`UdfContext` 或另一个函数对象。

### 12.5 Java UDF

Java UDF 只需要提供一个或多个 `apply` 方法。`Functions.Function0` 到 `Function22` 提供了显式泛型函数签名，也兼容标准 JDK `Function`、`BiFunction` 等具有 `apply` 方法的对象。

UDF 可以通过参数接收 `UdfContext`：

```java
public Boolean apply(String name, Integer age, UdfContext context) {
    context.setProperty("minAge", minAge);
    return age > minAge;
}
```

这正是规则执行和动态描述之间传递解释性信息的标准方式。

### 12.6 JavaScript UDF

当 `UdfDefinition.udf` 是字符串时：

```text
String source
  -> new JsUdf(name, source)
  -> UdfDelegate
  -> UDF 分组对象字段
```

JavaScript 源码的求值结果必须是可执行函数。注册名称负责 UDF 的外部绑定，匿名函数直接使用注册名称；命名函数用于递归或明确调用栈，其函数名必须与注册名称一致：

```javascript
// 注册为 math.sum：匿名箭头函数
(a, b) => a + b

// 注册为 math.sum：匿名 function
function (a, b) {
    return a + b;
}

// 注册为 math.sum：同名函数
function sum(a, b) {
    return a + b;
}
```

`function add(...)` 注册为 `sum` 会在套件构造阶段因名称不一致被拒绝，普通值表达式也不能作为 UDF。旧的“辅助函数加同名入口函数”脚本继续兼容；新定义优先使用直接返回函数对象的单一函数表达式。

`JsUdf` 使用两级线程本地状态：

```text
static ThreadLocal<Context>
    每个 Java 线程一个 JS UDF 执行环境

instance ThreadLocal<Value>
    每个 JsUdf 实例、每个线程一个入口函数对象
```

构造 `JsUdf` 时先在临时 Context 中验证源码返回可执行函数并检查名称，函数对象不跨 Context 保留。首次在某线程调用时，再在该线程 Context 中执行函数源码并取得可执行入口；后续调用直接执行已保存的 `Value`。旧格式脚本仍包裹在 IIFE 中，因此入口函数、辅助函数和可变状态都保留在当前 `JsUdf` 的词法作用域内，不写入共享 Context 的全局绑定。

这套模型源于 JavaScript 引擎 Context 的线程约束：

- 不让同一个 Context 同时跨线程执行；
- 不在每次 UDF 调用时重新加载函数；
- 每个 UDF 实例保留自己的入口函数句柄；
- 不同分组内的同名 JS UDF 互不覆盖，递归调用也始终解析到自身词法作用域。

分组不需要传入 `JsUdf`。分组已经在 `UdfContainer` 和 ByteBuddy 对象层完成，`JsUdf` 只负责叶子函数执行。

### 12.7 `@Udf` 注解的边界

`@Udf` 提供：

```text
value  UDF 名称
group  UDF 分组
```

并组合 Spring `@Component`，便于外部集成层发现 UDF。Core 本身不扫描 Spring 容器；它只接受已经转换完成的 `UdfDefinition` 列表。

这保持了内核装配模型与具体依赖注入框架之间的边界。

## 13. `RuleSuite` 与命名规则

### 13.1 统一定义模型

Core 只有一种声明态：`RuleDefinition`。

```text
RuleDefinition(useType=0)
  ruleId + JavaScript expression
            │ compile
            ▼
         ExprNode

RuleDefinition(useType=2)
  ruleId + rule ID DSL
            │ recursive compile
            ▼
  CompositeNode(ruleId, DSL root)
```

原子规则和复合规则共享 `ruleId` 命名空间、查找 API 和执行入口。`CompositeNode` 只表示“有名称的复合规则”，不是 Flow 类型；它保留外层规则 ID，并把 DSL 根节点作为内部规则树。

### 13.2 套件构造

`RuleSuite` 是规则运行快照，包含：

```text
RuleEngine
NodeBuilder
```

构造顺序为：

1. 构建一个 `RuleEngine`，注册全部定义并预编译原子 JavaScript；
2. `NodeBuilder` 从完整定义列表收集所有 `useType=2` 的 `ruleId -> DSL`；
3. 用完整复合规则表创建套件专属 `NodeGenerator`；
4. 构造阶段遍历全部复合规则 ID，递归预编译 `CompositeNode` 并检测循环；
5. 全部完成后得到一个可执行 `RuleSuite`。

先收集、后递归编译是必要条件：复合规则可能引用另一条复合规则，也可能引用定义顺序位于其后的规则。编译不能依赖输入列表顺序。构造阶段遍历全部复合规则仍然必要，用于验证未被其他规则引用的复合规则；`NodeBuilder` 的命名节点缓存保证已在递归中编译的节点不会重复构造。

### 13.3 构造即完整验证

```text
new RuleSuite(ruleDefinitions, udfDefinitions)
    注册全部规则与 UDF
    预编译原子 JavaScript 和动态描述
    递归预编译全部命名复合规则
    验证语法和循环引用
```

因此产品层可以通过“能否成功构造候选 `RuleSuite`”完成完整运行态校验。构造失败不会产生半成品套件。

### 13.4 发布边界与多套件隔离

Core 不维护全局 `current`，也不提供 `publish()`。`RuleSuite` 只是一个已经完整构造的可执行对象，多个套件可以同时存在并相互隔离。

产品层如果需要候选验证和原子发布，应在自己的套件管理器中先构造候选对象，再替换其运行引用。命名复合规则已经在候选套件自己的 `NodeBuilder` 中解析，执行时不会读取产品层的全局引用。

### 13.5 命名复合规则引用

复合规则 DSL 直接使用目标规则 ID：

```text
ruleId
```

解析与执行链：

```text
ruleId
  -> DefaultRuleVisitor
  -> NodeGenerator 查询当前复合规则表
     ├─ 命中 -> CompositeNode(ruleId, targetRuleNode) 并递归展开
     └─ 未命中 -> ExprNode(ruleId)
  -> 当前 RuleVisitor 执行节点
     └─ ExprNode -> RuleEngine.evalRule(ruleId)
  -> transform() 保留完整子详情
```

命名复合规则引用没有另一套运行时调用机制，也没有专用节点或语法标记。它使用 `CompositeNode.eval()`、当前 `RuleVisitor`、既有 `matched/result` 语义及详情树。Core 不丢弃执行详情；产品层如果需要折叠被引用编排，可依据自己的规则 ID 命名空间决定显示方式，而不是增加 AST 类型或特殊语法。复合规则表在解析前已完整收集，因此定义顺序不影响引用；循环引用由 `NodeGenerator` 的递归栈直接拒绝，不需要额外的 AST 遍历或调用图。

Core 不提供 `EvalFlowUdf`、`sys.flow.eval`、Flow 定义或 Flow 专用执行入口。产品层如果存在规则流，可在适配边界把编排树编译成 `useType=2` 的 `RuleDefinition`，并自行负责业务标识、发布状态和持久化。若产品规则与 Flow 分表存储，适配层还必须把两类主键映射到互不冲突的 `ruleId` 命名空间；参考 Web 使用 `r<id>` 表示原子规则、`f<id>` 表示规则流。

## 14. 并发与生命周期模型

| 对象 | 生命周期 | 并发策略 |
| --- | --- | --- |
| `JsRuntime.ENGINE` | 进程级 | GraalJS 编译基础设施共享 |
| `RuleSuite` | 一次配置发布 | 构造完成后作为运行快照使用 |
| `RuleEngine` | 跟随 RuleSuite | 规则表和 Source 缓存复用 |
| `NodeBuilder.compiledNodes` | 跟随 RuleSuite | 只缓存普通命名节点和预编译复合节点 |
| 普通规则 JS `Context` | 每次规则表达式执行 | 创建、执行、关闭，不共享可变 JS 状态 |
| `RuleVisitor` | 每次顶层求值 | 并行分支共享该实例，关键状态线程安全化 |
| `RuleVisitor.currentRule` | 每线程、每次求值 | `ThreadLocal` |
| `RuleVisitor.currentEval` | 每线程、每次求值 | `ThreadLocal` |
| `evalCache` | 每次顶层求值 | 无参数叶子按规则 ID 复用，参数化叶子按规则 ID 和规范化 JSON 复用 |
| JS UDF `Context` | 每 Java 线程 | 类级 `ThreadLocal` |
| JS UDF 入口 `Value` | 每 UDF 实例、每线程 | 实例级 `ThreadLocal` |

关键区别是：普通规则表达式使用短生命周期 Context，JavaScript UDF 使用每线程长生命周期 Context。前者强调单次执行隔离，后者强调可重复调用函数的线程安全和加载成本。

## 15. 监听与异常模型

### 15.1 监听器

`ListenerProvider.DEFAULT` 是进程级监听器总线，支持：

```text
PARSE_SUCCEED
PARSE_FAIL
EVAL_SUCCEED
EVAL_FAIL
```

事件携带表达式、结果或异常及耗时。监听器只观察解析和原子规则求值，不参与节点语义和业务结果。

每个监听器独立通知：单个监听器抛出 `RuntimeException` 时记录告警并继续通知其他监听器，不影响规则解析或执行。

### 15.2 异常

| 异常 | 边界 |
| --- | --- |
| `RuleParseException` | DSL 词法、语法或复合规则解析失败 |
| `RuleEvalException` | 规则 JavaScript/UDF 执行失败，或並行节点中断、超时等结构执行失败 |
| `RuleMatchException` | 保留的规则匹配异常类型 |

结构节点不把异常转换成“未命中”。未命中是正常业务状态，异常是执行失败，二者必须继续分离。

## 16. 完整执行示例

定义：

```java
RuleDefinition adult = new RuleDefinition(
    "101",
    "ageAtLeast($.age,$args.minAge,$$)",
    "${$.name}的年龄为${$.age}岁，本次阈值为${$args.minAge}岁"
);

RuleDefinition userCheck = new RuleDefinition(
    "user-check",
    "101(\"\"\"{\"minAge\":18}\"\"\")?allow:reject",
    "用户准入复合规则",
    RuleDefinition.USE_TYPE_COMPOSITE
);
```

UDF：

```java
class AdultUdf implements Functions.Function3<Integer, Integer, UdfContext, Boolean> {
    public Boolean apply(Integer age, Integer minAge, UdfContext context) {
        context.setProperty("checkedMinAge", minAge);
        return age >= minAge;
    }
}
```

装配：

```text
RuleSuite
  ├─ RuleEngine
  │    ├─ 101 -> JS Source
  │    ├─ allow -> JS Source
  │    ├─ reject -> JS Source
  │    └─ ageAtLeast -> UdfDelegate(AdultUdf)
  └─ user-check -> CompositeNode(
         user-check,
         CaseNode(101("""{"minAge":18}"""), allow, reject))
```

执行 `evalRule("user-check", user)`：

```text
1. RuleSuite 创建 RuleVisitor(user)
2. visit CaseNode
3. visit ExprNode("101", {minAge:18})
4. RuleVisitor.eval("101", arguments)
5. RuleEngine 创建 JS Context
6. 绑定 $=user、$$=RuleVisitor、$args={minAge:18}、ageAtLeast=UDF
7. 执行 ageAtLeast($.age,$args.minAge,$$)
8. UDF 写入 $$.checkedMinAge=18，并返回 Boolean
9. EvalResult 根据返回值生成 matched
10. CaseNode 选择 allow 或 reject
11. 执行结束后转换 EvalNode 详情树
12. 使用当前 $、$$、$args 渲染 101 的 desc
13. 返回 NodeResult
```

该链路体现了项目的关键分工：

- DSL 负责选择和编排；
- JavaScript 负责业务计算；
- `$args` 负责把模板规则实例化为当前节点；
- UDF 负责扩展和上下文协作；
- `matched` 负责控制；
- `result` 负责业务返回；
- `RuleResult` 负责解释。

## 17. 关键设计演进

Git 历史能够说明若干看似特殊的实现并非偶然：

### 17.1 2022：规则定义、逻辑组合与套件雏形

初始提交 `2076082` 已经把原子规则、规则组合、执行器和套件分开，核心方向是“规则定义可复用，规则集合按结构执行”。

### 17.2 2023：统一 `RuleNode` 执行树

提交 `be8ec99` 引入 `SerNode`、`ParNode`、`CaseNode`、`CompositeNode` 和 `EvalResult`，将纯逻辑判断扩展成可执行规则编排，同时保留统一递归接口。

### 17.3 2023：ANTLR 与 `∅`

提交 `f44e2a5` 使 ANTLR 替代手写运算符解析成为主解析路径；提交 `4b97903` 随后加入 `∅`，用于稳定结构根和单分支串并行表达。

### 17.4 2023：UDF 容器与 ByteBuddy

从提交 `3dda986` 开始的一组“增加UDF容器”变更把 UDF 装配从 `RuleEngine` 中抽离。UDF 分组最初就通过嵌套 Map 表达，ByteBuddy 专门负责把动态分组编译为 JavaScript 可自然访问的 Java 字段对象。

### 17.5 2023：JavaScript UDF 多线程模型

从 `8de202e` 开始的一系列“js函数多线程”提交逐步形成类级线程执行环境、实例级线程函数对象和 `UdfDelegate` 可变参数适配。当前 GraalJS 实现延续了这套生命周期，而不是重新发明 UDF 模型。

### 17.6 2026：JDK 21 与 GraalJS Polyglot

提交 `6849498` 将 JDK 和规则引擎升级到当前基线，并从 `ScriptEngine` 迁移到 GraalJS Polyglot：

- 共享 `Engine`；
- 每次普通规则执行创建 Context；
- 缓存可跨 Context 的 Source；
- 显式转换 Polyglot Value；
- 保留 Nashorn 兼容和 Java 互操作。

### 17.7 2026：规则快照与结构语义加固

提交 `7557027` 明确串并行节点执行语义，提交 `005c70f` 完善编排编译和运行快照。后续变更进一步收敛边界：

- `SerNode/ParNode` 是执行结构，不聚合业务真假；
- AST 组合节点不可变；
- 复合规则解析配置和命名节点缓存归属套件自己的 `NodeBuilder`；
- `RuleSuite` 只负责完整构造可执行套件，候选验证和原子发布由产品层管理器负责；
- 原子规则和复合规则统一为 `RuleDefinition`；
- Flow、Scene 等产品抽象及其专用 API 退出内核；
- 命名复合规则通过裸 `ruleId` 递归展开为普通 `CompositeNode`，不再通过 UDF 或特殊调用语法模拟。

### 17.8 2026：模板参数化规则

规则 ID DSL 新增 `ruleId("""{...}""")` 参数块，原子规则表达式和动态描述新增 `$args` 绑定。同一模板规则可以在一棵树中按节点携带不同参数执行，参数化节点不再被按 `ruleId` 的无参数缓存合并，执行结果直接归属当前 `EvalNode`。

ANTLR4 只负责安全识别参数块边界，JSON 对象仍由 `JsonUtils` 解析，JavaScript `Source` 继续预编译复用。这使 ANTLR、JSON 和 GraalJS 各自处理自己擅长的语言层次，不需要源码替换或自建 JavaScript 参数解析器。

### 17.9 2026：描述表达式标准化

旧的 `{$.a}` 自定义插值只能覆盖有限属性路径。标准 `${...}` 模板表达式让描述与普通规则共享 JavaScript 语义，同时显著减少自定义解析逻辑。

## 18. 核心不变量

后续修改必须保持以下约束：

1. 原子业务表达式使用 JavaScript，规则结构使用规则 ID DSL；不要混成一套自定义脚本语言。
2. `$` 始终表示本次业务输入，`$$` 始终表示本次规则上下文，`$args` 始终表示当前原子规则节点的模板参数。
3. `matched` 是逻辑/控制状态，`result` 是业务值。
4. `And/Or/Not/Hits` 解释命中状态；`Ser/Par` 只控制执行。
5. `Ser/Par` 正常完成返回 `result=null, matched=true`。
6. 规则未命中不是异常，执行异常不能被吞成未命中。
7. `RuleNode` 及其递归组合是执行语义唯一来源。
8. `∅` 是结构标记，不参与业务计算。
9. UDF 分组由 `UdfContainer` 和 ByteBuddy 动态对象实现；`JsUdf` 只执行叶子函数。
10. Java UDF、JS UDF、泛型参数转换和 UDF 作为参数必须继续走统一 `UdfDelegate`。
11. Java 互操作、Host Object 和 `BigDecimal` 属于可信规则能力。
12. 一个 `RuleSuite` 装配一个 `RuleEngine`；运行请求创建新的 `RuleVisitor`。
13. `RuleSuite` 必须完整构造成功才能交给产品层发布，Core 不维护全局发布状态。
14. 命名复合规则引用在套件构造阶段解析为普通 `CompositeNode`，保留完整子详情并统一检测循环引用。
15. Core 不定义 Flow、Scene 等产品抽象；产品编排只能在适配边界转换为复合 `RuleDefinition`。
16. 描述保留完整 JavaScript 表达式能力，不退化成只支持属性替换的模板。
17. 无参数叶子按 `ruleId` 复用，参数化叶子按规则 ID 和结构化参数复用；每次节点访问保留独立详情。

## 19. 修改检查表

### 19.1 修改 DSL 或节点

- 同步检查 `Rule.g4`；
- 检查 `DefaultRuleVisitor` 如何构造节点；
- 检查 `RuleNode.eval()` 语义；
- 检查 `expr()` 与 `toString()` 是否可稳定往返；
- 检查短路后的执行详情；
- 增加解析和执行测试。

### 19.2 修改结果模型

- 先判断需求属于业务结果、匹配状态还是诊断详情；
- 不把结构节点状态塞进 `result`；
- 不把未命中转换成异常；
- 检查 `RuleVisitor.transform()` 和 `NodeResult` 调用方；
- 保持序列化结构兼容。

### 19.3 修改 JavaScript 运行时

- 保留 `$`、`$$`、`$args` 和 UDF bindings；
- 验证 Java Host Object 原样返回；
- 验证 `BigDecimal` 和 `Java.type`；
- 验证并发 Source 执行；
- 验证 JS 对象、数组和数字转换；
- 区分普通规则 Context 与 JS UDF Context 的生命周期。

### 19.4 修改 UDF

- 验证无分组、单级分组和多级分组；
- 验证不同分组同名 UDF；
- 验证同组重复名称拒绝；
- 验证多参数数量重载；
- 验证泛型 List/Map/Bean 参数；
- 验证 UDF 作为另一个 UDF 的参数；
- 验证匿名 JS 函数、同名 JS 函数、名称不一致和非函数源码；
- 验证 JavaScript UDF 多线程执行。

### 19.5 修改 RuleSuite 或命名规则

- `RuleSuite` 只负责完整构造，不在 Core 内维护全局发布状态；
- 必须先收集全部复合规则，再使用本套件的 `NodeBuilder/NodeGenerator` 递归编译；
- 规则注册只保留在 `RuleEngine`，不要给 `NodeGenerator` 增加第二份注册集合；
- 临时 DSL 根节点不缓存，普通命名节点和命名复合节点可以在套件内复用；
- 验证复合规则引用另一复合规则及前向引用；
- 验证命名复合规则的递归解析、套件隔离、完整详情和循环引用拒绝；
- 保持 Flow 和业务路由在内核外。

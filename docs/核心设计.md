## 1. 文档目的

本文描述 `mosika-core` 的设计构思、语义边界和运行机制，重点回答以下问题：

- Mosika 为什么同时存在规则 DSL 和 JavaScript 表达式；
- `RuleNode` 为什么既能表示逻辑规则，又能表示串行、并行和条件执行；
- `EvalResult.matched` 与 `EvalResult.result` 为什么必须分离；
- `$`、`$$`、规则描述和 UDF 如何构成一套完整的表达式执行环境；
- UDF 为什么需要分组、`UdfDelegate` 和 ByteBuddy 动态类；
- `RuleSuite`、`RuleFlow` 与 `sys.flow.eval` 如何组成运行时套件；
- 并发执行、缓存、执行详情和套件发布分别在哪一层处理。

本文只讨论内核，不讨论 UI AST、页面布局、Web API、持久化和业务场景到规则流的映射。

本文采用三类证据解释设计：当前源码用于确认真实调用链，核心测试用于确认可观察契约，Git 历史用于区分长期设计与近期升级。只有三者能够相互印证的内容才作为确定设计；仅由代码形态推测的可能性不作为缺陷或设计结论。

## 2. 一句话架构

Mosika Core 是一个以 `RuleNode` 递归树为执行模型、以规则 ID DSL 为结构语言、以 JavaScript 为业务表达式语言、以 UDF 为扩展机制、以 `RuleSuite` 为发布单元的通用规则流引擎。

它不是把所有能力塞进一种语言，而是有意拆成两个层次：

```text
结构层：规则 ID DSL
    负责 与、或、非、命中数、条件、串行、并行及其作用域

计算层：JavaScript 表达式
    负责读取业务对象、调用 Java/UDF、计算和返回业务值
```

结构层决定“执行哪些规则以及如何组合”，计算层决定“每条原子规则具体做什么”。

## 3. 设计目标与基本原则

### 3.1 规则定义与规则编排分离

`RuleDefinition` 定义一条可独立执行的规则：

```text
ruleId      稳定标识
expression  JavaScript 业务表达式，或特定 useType 的声明内容
desc        可执行的规则描述
useType     规则定义类型
```

规则流 DSL 不复制业务表达式，只引用 `ruleId`：

```text
isAdult && isVerified ? grant : reject
```

这样可以独立维护业务规则和执行结构，也使复合规则、规则流、详情追踪都能使用稳定规则标识。

### 3.2 树是执行语义，不是展示结果

Mosika 使用递归树表达控制作用域，不使用通用 DAG：

```text
S(
  P(a, b),
  P(c, d)
)
```

该结构明确表示：先并行执行 `a、b` 并等待完成，再并行执行 `c、d`。并行子树的结束就是局部作用域的自然汇合，不需要多入边、隐式汇合点或额外图算法。

### 3.3 匹配状态与业务结果分离

任意节点都可能同时具备两个维度：

- 它作为条件时是否命中；
- 它实际产生了什么业务值。

因此 `EvalResult` 同时保存：

```text
matched  逻辑或控制状态
result   业务返回值
```

二者不能互相替代。逻辑节点主要解释 `matched`，动作和条件分支可能传递 `result`，串并行结构则只表示执行完成。

### 3.4 规则作者处于可信执行边界

规则表达式不是面向不可信用户的安全模板，而是可执行 JavaScript。设计上允许：

- 访问 Java 对象属性和方法；
- 使用 `Java.type(...)`；
- 传递和返回 `BigDecimal` 等 Java 类型；
- 调用 Java UDF 和 JavaScript UDF；
- 通过 `$$` 读取、写入本次规则上下文。

因此 GraalJS 的 Java 互操作能力是产品能力，不是默认需要消除的暴露面。若调用方需要不可信脚本隔离，应在内核外建立另一套授权和运行边界，不能通过缩减现有表达式语义实现。

### 3.5 编译配置与单次执行状态分离

规则、UDF 和规则流在 `RuleSuite` 构造阶段完成装配；一次实际求值则创建独立的 `RuleVisitor` 和 JavaScript Context。

这形成两类生命周期：

```text
套件生命周期：RuleSuite / RuleEngine / 编译 Source / UDF 对象图
请求生命周期：RuleVisitor / RuleContext / EvalNode 详情树 / JS Context
```

## 5. 两层表达式语言

### 5.1 外层：规则 ID DSL

ANTLR 语法位于 `src/main/antlr4/Rule.g4`。DSL 的原子项是规则 ID，组合能力包括：

| 语法 | 节点 | 含义 |
| --- | --- | --- |
| `!a` | `NotNode` | 对规则命中状态取反 |
| `a&&b` | `AndNode` | 逻辑与，遇到未命中即短路 |
| `a||b` | `OrNode` | 逻辑或，遇到命中即短路 |
| `a?b:c` | `CaseNode` | 根据 `a` 选择一个执行分支 |
| `a?b` | `CaseNode` | 仅有命中分支的条件执行 |
| `a->b` | `SerNode` | 串行执行结构 |
| `a=>b` | `ParNode` | 并行执行结构 |
| `hits(2,_,a,b,c)` | `HitsNode` | 至少命中两个子规则 |
| `_` | 命中边界 | 该侧不限制 |
| `∅` | 结构占位规则 | 稳定串并行结构，不参与业务计算 |

括号决定显式作用域。解析后不再依赖文本位置，而是由 `RuleNode` 类型和父子关系承载语义。

### 5.2 内层：JavaScript 业务表达式

每个普通 `RuleDefinition` 的 `expression` 是 JavaScript，例如：

```javascript
isAdult($.name, $.age, $$)
```

或者：

```javascript
$.amount.add(new (Java.type('java.math.BigDecimal'))('1.00'))
```

动作规则可以直接返回对象字面量：

```javascript
{stage: "CLAIM_EXTRACTION", status: "completed", claimCount: $.claimCount}
```

`RuleEngine` 会在编译边界自动为顶层对象字面量补充分组括号，规则作者不需要为避免对象被解析为代码块而手工书写 `({...})`。其他 JavaScript 表达式保持原样编译。

其中：

| 名称 | 含义 |
| --- | --- |
| `$` | 本次规则求值的业务对象，即 `RuleVisitor.data` |
| `$$` | 本次执行的规则上下文，即 `RuleVisitor` 本身 |
| 顶层 UDF 名称 | `UdfContainer` 编译后放入 JS bindings 的 UDF 或分组对象 |

`$` 和 `$$` 具有明显的表达式符号特征，不容易与普通业务字段冲突；同时保持规则文本紧凑。

### 5.3 为什么不把两层语言合并

如果直接在流程 DSL 中嵌入完整业务 JavaScript，会产生三个问题：

1. 结构解析器必须理解 JavaScript 的字符串、正则、对象字面量和运算符；
2. UI、持久化和规则复用无法稳定引用原子规则；
3. 执行详情难以用业务规则 ID 归档和解释。

当前设计让 DSL 只解析有限、稳定的组合语法，把复杂计算交给成熟的 JavaScript 引擎。

## 6. 规则描述也是可执行表达式

`RuleDefinition.desc` 不是静态注释。它是使用同一份 `$`、`$$` 执行的简化规则表达式，主要用于生成可解释的执行详情。

示例：

```java
new RuleDefinition(
    "101",
    "isAdult($.name,$.age,$$)",
    "${$.name}的年龄(${$.age})小于${$$.minAge}岁"
)
```

执行顺序为：

```text
1. 执行规则 expression
2. UDF 可通过 $$ 写入 minAge 等上下文属性
3. RuleVisitor 构造执行详情
4. 使用当前 $ 和 $$ 执行 desc
5. 生成 RuleResult.desc
```

因此描述能够引用规则执行过程中写入的上下文，而不需要把诊断字段塞进业务 `result`。

当前描述采用标准 JavaScript 模板插值：

```text
${$.name}
${$$.agent}
${$.name.toUpperCase()}
```

`compileDesc()` 使用 `String.raw` 模板字符串编译为 GraalJS `Source`，既保留静态文本中的反斜杠和换行，又让 `${...}` 内保持完整 JavaScript 语义，包括方法调用、对象字面量和正则表达式。

该语法替代了旧的 `{$.a}` 自定义正则拆分方式。它是明确的语法升级边界；仓库外持久化的旧描述需要与代码同步迁移。

## 7. `RuleNode`：统一递归执行模型

### 7.1 统一接口

所有节点实现：

```java
EvalResult eval(RuleContext context);
String expr();
```

同时通过默认组合方法形成节点代数：

```java
and(node)
or(node)
not()
next(node)
```

组合操作返回新的 `RuleNode`，因此规则可以用解析器构建，也可以由 Java/UI AST 直接构建。

### 7.2 节点分类

| 类别 | 节点 | 核心职责 |
| --- | --- | --- |
| 原子规则 | `ExprNode` | 根据规则 ID 调用 `RuleContext.eval()` |
| 复合规则引用 | `CompositeNode` | 为命名复合规则包裹展开后的内部规则树 |
| 逻辑节点 | `AndNode`、`OrNode`、`NotNode`、`HitsNode` | 解释子节点 `matched` |
| 条件节点 | `CaseNode` | 选择并执行一个分支 |
| 执行结构 | `SerNode`、`ParNode` | 控制所有子节点的执行顺序 |

这种统一接口并不意味着所有节点具有相同语义。节点类型本身就是语义来源。

### 7.3 逻辑节点

#### `AndNode`

按顺序访问子节点：

- 任一子节点 `matched=false`，立即返回未命中；
- 全部命中，返回命中；
- 返回值表达逻辑判断，不透传某个子节点的业务 `result`。

#### `OrNode`

按顺序访问子节点：

- 任一子节点 `matched=true`，立即返回命中；
- 全部未命中，返回未命中。

#### `NotNode`

访问子节点并反转其 `matched`。连续两次 `not()` 会回到原节点。

#### `HitsNode`

统计子节点命中数是否落在 `[minHits, maxHits]` 区间：

- `null` 边界对应 DSL 中的 `_`；
- 两侧不能同时不设限；
- 最大命中数不能超过规则数；
- 当最小值已经保证、最大值也不可能超出时提前返回命中；
- 当最大值已超出，或剩余节点不可能达到最小值时提前返回未命中。

`HitsNode` 使用 `context.visit(node)`，因此短路和详情树保持一致。

### 7.4 条件节点 `CaseNode`

`CaseNode` 先访问条件节点，只执行被选择的分支：

```text
condition=true  -> trueCase
condition=false -> falseCase
```

如果分支存在，`CaseNode` 传递该分支的 `result` 和 `matched`；如果没有对应分支，则返回 `result=null, matched=false`。

这使条件节点既可以做纯判断，也可以承载动作和更复杂的流程子树。

### 7.5 串行结构 `SerNode`

`SerNode`：

- 按声明顺序访问所有非 `∅` 子节点；
- 不因为某个子节点未命中而停止；
- 不使用最后一个子节点结果代表整个串行结构；
- 正常完成统一返回 `result=null, matched=true`；
- 子节点异常继续向上传播。

串行结构表达的是“这些步骤都执行完成”，而不是逻辑与。

### 7.6 并行结构 `ParNode`

`ParNode`：

- 使用公共执行池并发访问所有非 `∅` 分支；
- 等待全部分支完成；
- 不把子分支命中状态聚合为真假；
- 正常完成统一返回 `result=null, matched=true`；
- 子分支异常由 `CompletableFuture` 汇集，对外抛出时解包并保留原始业务异常；
- 等待被中断时恢复当前线程的中断标记，并使用 `RuleEvalException` 表达结构执行失败；
- 等待超时或被中断时取消尚未开始执行的分支，不强制终止已在运行的分支；
- 当前实现等待上限为一分钟。

并行结构表达的是“这些分支并发执行并在本层汇合”，而不是逻辑或。

### 7.7 `next()` 的协变追加语义

`RuleNode.next()` 默认创建 `SerNode`，但组合节点重写为自身追加：

```text
SerNode.next(x) -> 在串行列表末尾追加 x
ParNode.next(x) -> 在并行列表末尾追加 x
```

因此不能只根据方法名把 `ParNode.next()` 理解成“创建后续串行步骤”。它在 `ParNode` 上表示继续扩展当前并行组合。

当一个流程需要以并行结构开头、之后再进入串行步骤时，可以使用结构标记稳定外层串行根：

```text
∅->(a=>b)->c
```

解析结果是：

```text
SerNode(
  ∅,
  ParNode(a,b),
  c
)
```

### 7.8 不可变 AST 与缓存安全

当前组合节点使用 `List.copyOf(...)` 保存子节点；追加操作创建新节点而不是修改旧节点。

这样做是因为同一套件会缓存解析后的 `RuleNode`。如果调用方在组合时修改共享节点，后续执行会被静默污染。不可变结构使缓存、并发执行和 UI 到内核的单向编译可以共享同一套节点语义。

## 8. 解析与复合规则

### 8.1 ANTLR 解析链路

```text
DSL 文本
  -> RuleLexer / RuleParser
  -> DefaultRuleVisitor
  -> NodeGenerator
  -> RuleNode 树
```

`Antlr4Parser` 负责配置统一错误监听器；解析失败后由 `NodeBuilder` 包装成 `RuleParseException`，同时发送解析事件。

### 8.2 `NodeBuilder` 与 `RuleEvaluator` 的职责

`NodeBuilder.build(expr)` 是通用解析入口，使用当前默认 `NodeGenerator`，但不缓存并返回共享可变 AST。

套件运行路径由 `RuleEvaluator` 负责：

- 每个 `RuleEvaluator` 持有自己的 `NodeGenerator`；
- 每个 `RuleEvaluator` 持有自己的 `nodeCache`；
- 同一 DSL 在同一套件内只解析一次；
- 不同套件的复合规则定义不会污染彼此。

因此解析配置属于套件，而不是进程全局状态。

### 8.3 复合规则展开

`useType=2` 的 `RuleDefinition` 表示命名复合规则。它的 `expression` 不是 JavaScript，而是另一段规则 ID DSL。

`NodeGenerator.create(compositeRules)` 在遇到复合规则 ID 时：

1. 创建 `CompositeNode` 保留外层规则 ID；
2. 递归解析其内部 DSL；
3. 使用栈记录当前解析路径；
4. 遇到循环引用时立即失败。

例如：

```text
a = 1 || b
b = 2 && 3
```

会形成：

```text
CompositeNode(a,
  Or(
    Expr(1),
    CompositeNode(b, And(Expr(2), Expr(3)))
  )
)
```

命名复合规则既保留可解释的外层身份，又拥有可递归追踪的内部详情。

## 9. `RuleVisitor`：单次执行的核心上下文

每次 `RuleEvaluator.eval(...)` 创建新的 `RuleVisitor`。它同时承担四个角色：

```text
RuleContext     节点递归访问接口
UdfContext      UDF 可访问的规则上下文
Map             $$ 暴露的可读写属性容器
Trace Builder   EvalNode 执行详情树构造器
```

### 9.1 叶子规则缓存

`ExprNode.eval()` 调用 `context.eval(ruleId)`。`RuleVisitor` 使用 `evalCache.computeIfAbsent(...)` 保证同一规则 ID 在一次执行中只真正求值一次。

这有两个作用：

- 避免同一原子规则在复合表达式中重复执行；
- 避免有副作用的规则或 UDF 在同一次执行中被重复触发。

非叶子节点结果也写入缓存，但主要用于构造详情树；节点递归仍由 `visit()` 控制。

### 9.2 当前规则

进入 `ExprNode` 时，`currentRule` 写入当前规则 ID。UDF 可以通过 `UdfContext.getRule()` 获知是谁调用了自己。

`currentRule` 使用 `ThreadLocal`，使并行分支分别维护自己的当前规则。

### 9.3 共享业务上下文 `$$`

`RuleVisitor` 继承 `LinkedHashMap<String,Object>`，并实现：

```text
getProperty
setProperty
removeProperty
```

JavaScript 规则通过 `$$.property` 访问，Java UDF 通过 `UdfContext` 访问。并行写入方法使用同步保护；并行分支共享同一份本次执行上下文。

### 9.4 执行详情树

每次 `visit(node)` 都创建 `EvalNode` 并挂到当前父节点。非叶子节点进入时更新 `currentEval`，退出时在 `finally` 中回溯。

`finally` 回溯保证异常路径不会把后续节点挂到错误父节点。

并行执行时，每个子线程先恢复并行节点对应的父执行节点，再访问自己的分支。`EvalNode.children` 使用线程安全集合保存并行分支详情。

### 9.5 详情物化

执行结束后，`getRuleResults()` 将 `EvalNode` 树转换为 `RuleResult` 树：

- 从 `evalCache` 读取每个节点结果；
- 对原子规则和命名复合规则求值描述，渲染期间将 `currentRule` 限定为正在物化的规则 ID，并在结束后恢复原值；
- 递归附加 `subRules`；
- 保留真实短路后的访问路径，而不是静态 AST 全量展开。

因此详情表达“本次实际执行了什么”，而不是“理论上可能执行什么”。

## 10. 结果模型

### 10.1 `EvalResult`

字段：

| 字段 | 含义 |
| --- | --- |
| `expr` | 当前节点或规则表达式 |
| `result` | 业务返回值 |
| `matched` | 作为条件时的命中状态 |

普通 JavaScript 返回值通过默认规则转换为 `matched`：

| 返回值 | 命中规则 |
| --- | --- |
| `null` | 未命中 |
| `Boolean` | 使用原值 |
| `Number` | 大于零时命中 |
| `String` | `no/false/null/0/fail` 视为未命中，其余命中 |
| `Collection` | 非空时命中 |
| `Map` | 非空时命中 |
| 其他对象 | 命中 |

数字判定按具体数值类型精确比较：`BigDecimal` 和 `BigInteger` 使用 `signum()`，整数类型使用 `longValue()`，其他数字使用 `doubleValue()`，避免把任意 `Number` 统一缩窄后再判定。

结构节点和部分逻辑节点可以使用显式构造函数分别指定 `result` 与 `matched`，不必依赖默认转换。

### 10.2 `RuleResult`

`RuleResult` 继承 `EvalResult`，增加：

```text
desc      动态规则描述
subRules  实际执行的子规则详情
```

它属于可解释性模型，不改变业务返回值。

### 10.3 `NodeResult`

`NodeResult` 是 `RuleEvaluator` 对外返回模型：

```text
expr     根节点 DSL
result   根节点业务结果
details  执行详情
```

带外部上下文的求值入口可以关闭详情构造，并在执行后把 `RuleVisitor` 属性写回调用方提供的 Map。

### 10.4 `NaResult`

`NaResult` 是区别于 Java `null` 的“无业务结果”哨兵。内置 `null` 和 `∅` 规则返回该对象。

`RuleEvaluator` 发现根节点结果本身是 `NodeResult` 时直接返回，使 `NaResult` 这类哨兵能够穿过普通 `EvalResult` 包装。

## 11. `RuleEngine`：JavaScript 规则执行器

### 11.1 构造阶段

一个 `RuleSuite` 创建一个 `RuleEngine`。构造过程：

1. 注册内置规则 `true`、`false`、`null`、`∅`；
2. 注册业务 `RuleDefinition`；
3. 普通规则按表达式语义自动包装并预解析 JavaScript `Source`；
4. 复合规则跳过 JavaScript 编译，由外层 DSL 解析器处理；
5. 所有规则描述预编译；
6. `UdfContainer` 构建完整 UDF 命名空间对象。

因此语法错误尽量在套件构造阶段暴露，而不是等到流量执行时才发现。

### 11.2 执行阶段

每次 `evalRule()` 或 `evalExpr()`：

1. 创建新的 GraalJS `Context`；
2. 绑定 `$`；
3. 绑定 `$$`；
4. 绑定所有顶层 UDF；
5. 执行缓存的 `Source`；
6. 把 Polyglot `Value` 转换为脱离 Context 生命周期的 Java 值；
7. 关闭本次 Context。

这保证普通规则执行之间不共享 JavaScript 可变全局状态，同时允许复用编译结果。

### 11.3 编译缓存

`RuleEngine` 维护两套并发缓存：

```text
compiledScripts  key=JavaScript expression
compiledDesc     key=description text
```

缓存值是可跨 Context 使用的 GraalJS `Source`，而不是绑定到某个 Context 的函数对象。

### 11.4 GraalJS 运行时

`JsRuntime` 维护进程级共享 `Engine`。所有普通规则 Context 使用该 Engine，以复用 GraalJS 的解析和编译基础设施。

Context 配置保留：

```text
HostAccess.ALL
任意 Java 类查找
Nashorn compatibility
ECMAScript latest
```

`ECMAScript latest` 与 Nashorn 兼容模式同时设置，是为了在保持旧 Java 互操作能力的同时支持模板字符串等现代语法。

### 11.5 Polyglot 结果转换

`JsRuntime.toJava()` 的目标不是把 Context 继续暴露给调用方，而是在 Context 关闭前转换结果：

```text
Host Object -> 原 Java 对象
Boolean     -> Boolean
String      -> String
Number      -> Integer / Long / Double
Array       -> ArrayList
Members     -> LinkedHashMap
```

先判断 `isHostObject()`，因此 Java 传入并原样返回的 `BigDecimal` 等类型不会被强制降级成 JavaScript 数字。

## 12. UDF 设计

### 12.1 `UdfDefinition` 是统一声明模型

```text
group  可选分组路径，例如 sys.flow
name   UDF 名称，例如 eval
udf    Java 对象或 JavaScript 源码字符串
```

它不区分 Java UDF 和 JS UDF 的外部注册方式。类型差异由 `UdfContainer` 在装配阶段处理。

### 12.2 UDF 分组

分组使用点号形成多级命名空间：

```java
new UdfDefinition("policy.sys", "replace", udf)
```

规则中调用：

```javascript
policy.sys.replace($)
```

注册时，`UdfContainer` 把分组拆成嵌套 Map：

```text
policy
  └─ sys
      └─ replace
```

同名 UDF 可以存在于不同分组；同一分组内名称必须唯一。一个路径位置不能同时既是函数又是子分组。

### 12.3 为什么使用 ByteBuddy

GraalJS 表达式需要用自然属性语法访问分组：

```javascript
policy.sys.replace(...)
```

普通 Map 在不同 JavaScript 引擎和 Java 互操作模式下不一定等价于稳定的 Java 属性对象。`UdfContainer.compileUdf()` 使用 ByteBuddy 递归生成具有公共字段的动态类：

```text
UDF$Policy
  public Object sys

UDF$Policy$Sys
  public Object replace
```

字段值再通过 `MethodHandle` 写入。最终每个顶层分组都是一个真实 Java 对象，GraalJS 可以沿字段自然访问。

ByteBuddy 因此承担的是“动态命名空间对象编译”，不是 Java UDF 方法代理；移除它会改变分组对象的 JavaScript 属性语义。

### 12.4 `UdfDelegate`

所有叶子 UDF 最终由 `UdfDelegate.Wrapper` 包装。它负责：

- 查找名为 `apply` 且参数数量匹配的方法；
- 忽略编译器生成的 bridge method；
- 根据目标泛型参数类型转换 JavaScript 参数；
- 支持一个 UDF 实现多个不同参数数量的函数接口；
- 当 UDF 作为另一个 UDF 的参数传入时，解开 Wrapper，传递真实函数对象；
- 对 `JsUdf` 的可变参数调用做适配。

因此 Java UDF 可以同时支持：

```java
apply(User user)
apply(User user, String name)
```

也可以接收 `List<T>`、`Map<K,V>`、`UdfContext` 或另一个函数对象。

### 12.5 Java UDF

Java UDF 只需要提供一个或多个 `apply` 方法。`Functions.Function0` 到 `Function22` 提供了显式泛型函数签名，也兼容标准 JDK `Function`、`BiFunction` 等具有 `apply` 方法的对象。

UDF 可以通过参数接收 `UdfContext`：

```java
public Boolean apply(String name, Integer age, UdfContext context) {
    context.setProperty("minAge", minAge);
    return age > minAge;
}
```

这正是规则执行和动态描述之间传递解释性信息的标准方式。

### 12.6 JavaScript UDF

当 `UdfDefinition.udf` 是字符串时：

```text
String source
  -> new JsUdf(name, source)
  -> UdfDelegate
  -> UDF 分组对象字段
```

`JsUdf` 使用两级线程本地状态：

```text
static ThreadLocal<Context>
    每个 Java 线程一个 JS UDF 执行环境

instance ThreadLocal<Value>
    每个 JsUdf 实例、每个线程一个入口函数对象
```

首次在某线程调用时，`JsUdf` 在该线程 Context 中执行包裹在 IIFE 中的函数源码，并直接取得该段源码返回的可执行入口；后续调用直接执行已保存的 `Value`。入口函数、辅助函数和可变状态都保留在当前 `JsUdf` 的词法作用域内，不写入共享 Context 的全局绑定。

这套模型源于 JavaScript 引擎 Context 的线程约束：

- 不让同一个 Context 同时跨线程执行；
- 不在每次 UDF 调用时重新加载函数；
- 每个 UDF 实例保留自己的入口函数句柄；
- 不同分组内的同名 JS UDF 互不覆盖，递归调用也始终解析到自身词法作用域。

分组不需要传入 `JsUdf`。分组已经在 `UdfContainer` 和 ByteBuddy 对象层完成，`JsUdf` 只负责叶子函数执行。

### 12.7 `@Udf` 注解的边界

`@Udf` 提供：

```text
value  UDF 名称
group  UDF 分组
```

并组合 Spring `@Component`，便于外部集成层发现 UDF。Core 本身不扫描 Spring 容器；它只接受已经转换完成的 `UdfDefinition` 列表。

这保持了内核装配模型与具体依赖注入框架之间的边界。

## 13. 决策表规则

`useType=1` 表示决策表。`RuleSuite.create()` 在构造运行时定义时：

1. 使用 `RuleTableUdf.fromJson()` 解析表格定义；
2. 生成内部 UDF 名称 `udf_rule_table_$<ruleId>`；
3. 把决策表对象注册为普通 UDF；
4. 将规则表达式改写为 `udf_rule_table_$<ruleId>($)`；
5. 交给普通 `RuleEngine` 执行链路。

`RuleTableUdf` 按数据行顺序匹配：

- `keys` 指定输入字段；
- 输入字段缺失或值为 `null` 时统一按空字符串匹配；
- 条件单元格为 `null` 或空字符串时表示通配；
- 第一条匹配行返回 `values` 对应的有序 Map；
- 没有匹配行返回 `null`；
- 加载时校验 `keys` / `values` / `data` 完整性，以及每行列数是否等于条件列与返回列之和。

该设计把特殊规则形态在装配阶段降解为普通 UDF 调用，避免在 `RuleEngine` 和 `RuleNode` 中增加另一套执行协议。

## 14. `RuleSuite` 与 `RuleFlow`

### 14.1 声明态与运行态

```text
RuleFlowDefinition
  id
  dsl
      │ compile
      ▼
RuleFlow
  id
  RuleNode root
```

`RuleFlowDefinition` 是可加载、可持久化的声明；`RuleFlow` 是已经绑定当前套件复合规则配置的运行对象。

### 14.2 套件构造

`RuleSuite` 是规则运行快照，包含：

```text
RuleEvaluator
Map<String, RuleFlow>
```

构造顺序为：

1. 复制并转换 `RuleDefinition`；
2. 生成决策表 UDF；
3. 收集复合规则定义；
4. 构建一个 `RuleEngine`；
5. 创建套件专属 `NodeGenerator` 和 `RuleEvaluator`；
6. 编译全部 `RuleFlowDefinition`；
7. 检查重复 flow ID；
8. 将 flow Map 冻结；
9. 完整成功后才发布为当前套件。

这样不会把构造到一半的套件暴露给运行流量。

### 14.3 候选套件与原子发布

```text
RuleSuite.prepare(...)
    构造并完整编译候选套件，不修改当前运行快照

RuleSuite.validate(...)
    只验证能否完整构造

RuleSuite.publish(candidate)
    原子替换 volatile current
```

这套机制适合“先校验、再持久化、最后发布”的管理流程，同时保持运行中的套件稳定。

### 14.4 `RuleSuite.current`

`RuleSuite.get()` 返回进程当前已发布套件。它主要服务于内核级跨规则流 UDF，而不是任意业务套件查找器。

该模型假设一个运行单元维护一份当前生效规则套件。构造候选套件不会替换它，只有显式发布或正常公开构造完成后才更新。

### 14.5 `sys.flow.eval`

`EvalFlowUdf` 注册为：

```text
group = sys.flow
name  = eval
```

规则表达式可以调用：

```javascript
sys.flow.eval('flowId', $, $$)
```

调用链：

```text
当前规则 JavaScript
  -> UdfDelegate
  -> EvalFlowUdf.apply(...)
  -> RuleSuite.get()
  -> current.evalFlow(...)
  -> 内层 RuleEvaluator
  -> 返回内层 NodeResult.result
```

UDF 只把内层业务 `result` 返回给外层 JavaScript；内层详情和控制结构不会被塞进外层业务值。

该能力用于规则流之间的内核级组合。业务场景、产品、策略到 `flowId` 的路由属于内核外部，不应重新进入 `RuleFlow` 或 `RuleSuite`。

## 15. 并发与生命周期模型

| 对象 | 生命周期 | 并发策略 |
| --- | --- | --- |
| `JsRuntime.ENGINE` | 进程级 | GraalJS 编译基础设施共享 |
| `RuleSuite.current` | 当前发布快照 | `volatile` 原子替换 |
| `RuleSuite` | 一次配置发布 | 构造完成后作为运行快照使用 |
| `RuleEngine` | 跟随 RuleSuite | 规则表和 Source 缓存复用 |
| `RuleEvaluator.nodeCache` | 跟随 RuleSuite | `ConcurrentHashMap` |
| 普通规则 JS `Context` | 每次规则表达式执行 | 创建、执行、关闭，不共享可变 JS 状态 |
| `RuleVisitor` | 每次顶层求值 | 并行分支共享该实例，关键状态线程安全化 |
| `RuleVisitor.currentRule` | 每线程、每次求值 | `ThreadLocal` |
| `RuleVisitor.currentEval` | 每线程、每次求值 | `ThreadLocal` |
| `evalCache` | 每次顶层求值 | 并发 Map，规则 ID 只求值一次 |
| JS UDF `Context` | 每 Java 线程 | 类级 `ThreadLocal` |
| JS UDF 入口 `Value` | 每 UDF 实例、每线程 | 实例级 `ThreadLocal` |

关键区别是：普通规则表达式使用短生命周期 Context，JavaScript UDF 使用每线程长生命周期 Context。前者强调单次执行隔离，后者强调可重复调用函数的线程安全和加载成本。

## 16. 监听与异常模型

### 16.1 监听器

`ListenerProvider.DEFAULT` 是进程级监听器总线，支持：

```text
PARSE_SUCCEED
PARSE_FAIL
EVAL_SUCCEED
EVAL_FAIL
```

事件携带表达式、结果或异常及耗时。监听器只观察解析和原子规则求值，不参与节点语义和业务结果。

每个监听器独立通知：单个监听器抛出 `RuntimeException` 时记录告警并继续通知其他监听器，不影响规则解析或执行。

### 16.2 异常

| 异常 | 边界 |
| --- | --- |
| `RuleParseException` | DSL 词法、语法或复合规则解析失败 |
| `RuleEvalException` | 规则 JavaScript/UDF 执行失败，或並行节点中断、超时等结构执行失败 |
| `NoRuleFlowException` | 请求的 flow ID 不存在 |
| `RuleMatchException` | 保留的规则匹配异常类型 |

结构节点不把异常转换成“未命中”。未命中是正常业务状态，异常是执行失败，二者必须继续分离。

## 17. 完整执行示例

定义：

```java
RuleDefinition adult = new RuleDefinition(
    "101",
    "isAdult($.name,$.age,$$)",
    "${$.name}的年龄(${$.age})小于${$$.minAge}岁"
);

RuleFlowDefinition flow = new RuleFlowDefinition(
    "user-check",
    "101?allow:reject"
);
```

UDF：

```java
class AdultUdf implements Functions.Function3<String, Integer, UdfContext, Boolean> {
    public Boolean apply(String name, Integer age, UdfContext context) {
        context.setProperty("minAge", 18);
        return age >= 18;
    }
}
```

装配：

```text
RuleSuite
  ├─ RuleEngine
  │    ├─ 101 -> JS Source
  │    ├─ allow -> JS Source
  │    ├─ reject -> JS Source
  │    └─ isAdult -> UdfDelegate(AdultUdf)
  └─ user-check -> CaseNode(101, allow, reject)
```

执行 `evalFlow("user-check", user)`：

```text
1. RuleEvaluator 创建 RuleVisitor(user)
2. visit CaseNode
3. visit ExprNode("101")
4. RuleVisitor.eval("101")
5. RuleEngine 创建 JS Context
6. 绑定 $=user、$$=RuleVisitor、isAdult=UDF
7. 执行 isAdult($.name,$.age,$$)
8. UDF 写入 $$.minAge=18，并返回 Boolean
9. EvalResult 根据返回值生成 matched
10. CaseNode 选择 allow 或 reject
11. 执行结束后转换 EvalNode 详情树
12. 使用当前 $、$$ 渲染 101 的 desc
13. 返回 NodeResult
```

该链路体现了项目的关键分工：

- DSL 负责选择和编排；
- JavaScript 负责业务计算；
- UDF 负责扩展和上下文协作；
- `matched` 负责控制；
- `result` 负责业务返回；
- `RuleResult` 负责解释。

## 18. 关键设计演进

Git 历史能够说明若干看似特殊的实现并非偶然：

### 18.1 2022：规则定义、逻辑组合与套件雏形

初始提交 `2076082` 已经把原子规则、规则组合、执行器和套件分开，核心方向是“规则定义可复用，规则集合按结构执行”。

### 18.2 2023：统一 `RuleNode` 执行树

提交 `be8ec99` 引入 `SerNode`、`ParNode`、`CaseNode`、`CompositeNode` 和 `EvalResult`，将纯逻辑判断扩展成可执行规则流，同时保留统一递归接口。

### 18.3 2023：ANTLR 与 `∅`

提交 `f44e2a5` 使 ANTLR 替代手写运算符解析成为主解析路径；提交 `4b97903` 随后加入 `∅`，用于稳定结构根和单分支串并行表达。

### 18.4 2023：UDF 容器与 ByteBuddy

从提交 `3dda986` 开始的一组“增加UDF容器”变更把 UDF 装配从 `RuleEngine` 中抽离。UDF 分组最初就通过嵌套 Map 表达，ByteBuddy 专门负责把动态分组编译为 JavaScript 可自然访问的 Java 字段对象。

### 18.5 2023：JavaScript UDF 多线程模型

从 `8de202e` 开始的一系列“js函数多线程”提交逐步形成类级线程执行环境、实例级线程函数对象和 `UdfDelegate` 可变参数适配。当前 GraalJS 实现延续了这套生命周期，而不是重新发明 UDF 模型。

### 18.6 2026：JDK 21 与 GraalJS Polyglot

提交 `6849498` 将 JDK 和规则引擎升级到当前基线，并从 `ScriptEngine` 迁移到 GraalJS Polyglot：

- 共享 `Engine`；
- 每次普通规则执行创建 Context；
- 缓存可跨 Context 的 Source；
- 显式转换 Polyglot Value；
- 保留 Nashorn 兼容和 Java 互操作。

### 18.7 2026：规则流快照与结构语义加固

提交 `7557027` 明确串并行节点执行语义，提交 `005c70f` 完善规则流编译和运行快照。后续变更明确：

- `SerNode/ParNode` 是执行结构，不聚合业务真假；
- AST 组合节点不可变；
- 复合规则解析配置和缓存归属 `RuleEvaluator` 实例；
- `RuleSuite` 支持候选构造、验证和原子发布；
- `Scene` 业务抽象退出内核，保留通用命名 `RuleFlow`；
- `sys.scene.eval` 演进为 `sys.flow.eval`。

### 18.8 2026：描述表达式标准化

旧的 `{$.a}` 自定义插值只能覆盖有限属性路径。标准 `${...}` 模板表达式让描述与普通规则共享 JavaScript 语义，同时显著减少自定义解析逻辑。

## 19. 核心不变量

后续修改必须保持以下约束：

1. 原子业务表达式使用 JavaScript，规则结构使用规则 ID DSL；不要混成一套自定义脚本语言。
2. `$` 始终表示本次业务输入，`$$` 始终表示本次规则上下文。
3. `matched` 是逻辑/控制状态，`result` 是业务值。
4. `And/Or/Not/Hits` 解释命中状态；`Ser/Par` 只控制执行。
5. `Ser/Par` 正常完成返回 `result=null, matched=true`。
6. 规则未命中不是异常，执行异常不能被吞成未命中。
7. `RuleNode` 及其递归组合是执行语义唯一来源。
8. `∅` 是结构标记，不参与业务计算。
9. UDF 分组由 `UdfContainer` 和 ByteBuddy 动态对象实现；`JsUdf` 只执行叶子函数。
10. Java UDF、JS UDF、泛型参数转换和 UDF 作为参数必须继续走统一 `UdfDelegate`。
11. Java 互操作、Host Object 和 `BigDecimal` 属于可信规则能力。
12. 一个 `RuleSuite` 装配一个 `RuleEngine`；运行请求创建新的 `RuleVisitor`。
13. 套件候选必须完整编译成功后才能发布。
14. `sys.flow.eval` 调用当前已发布套件中的命名规则流。
15. 业务场景映射不进入 `RuleFlow`、`RuleFlowDefinition` 或 `RuleSuite`。
16. 描述保留完整 JavaScript 表达式能力，不退化成只支持属性替换的模板。

## 20. 修改检查表

### 20.1 修改 DSL 或节点

- 同步检查 `Rule.g4`；
- 检查 `DefaultRuleVisitor` 如何构造节点；
- 检查 `RuleNode.eval()` 语义；
- 检查 `expr()` 与 `toString()` 是否可稳定往返；
- 检查短路后的执行详情；
- 增加解析和执行测试。

### 20.2 修改结果模型

- 先判断需求属于业务结果、匹配状态还是诊断详情；
- 不把结构节点状态塞进 `result`；
- 不把未命中转换成异常；
- 检查 `RuleVisitor.transform()` 和 `NodeResult` 调用方；
- 保持序列化结构兼容。

### 20.3 修改 JavaScript 运行时

- 保留 `$`、`$$` 和 UDF bindings；
- 验证 Java Host Object 原样返回；
- 验证 `BigDecimal` 和 `Java.type`；
- 验证并发 Source 执行；
- 验证 JS 对象、数组和数字转换；
- 区分普通规则 Context 与 JS UDF Context 的生命周期。

### 20.4 修改 UDF

- 验证无分组、单级分组和多级分组；
- 验证不同分组同名 UDF；
- 验证同组重复名称拒绝；
- 验证多参数数量重载；
- 验证泛型 List/Map/Bean 参数；
- 验证 UDF 作为另一个 UDF 的参数；
- 验证 JavaScript UDF 多线程执行。

### 20.5 修改 RuleSuite 或 RuleFlow

- 候选套件构造期间不得替换 `current`；
- 全部 flow 必须使用本套件的 `NodeGenerator` 编译；
- 重复 flow ID 必须失败；
- 发布后的 flow Map 不允许外部修改；
- 验证 `sys.flow.eval` 的两参数和三参数形式；
- 保持业务路由在内核外。

## 4. 已确认并修复的问题

### 4.1 `SomeNode` 无上限被冻结为构造时节点数

**现象**

`maxHits == null` 表示不限制最大命中数，旧实现却把内部 `max` 设为构造参数 `nodes.length`

在可变构建阶段追加节点后，`some(2,_,t1,t2)` 会因为内部上限仍是 1 而错误返回未命中

**设计意图**

- `SomeNode` 类注释明确说明 `null` 边界表示不限制
- RuleNode 结构是可变构建器语义
- 节点内部集合的可变性不是防御性暴露

**修复**

无上限的内部上限改为 `Integer.MAX_VALUE`，不新增热路径分配，不改变短路算法

**回归**

新增 `testSomeNodeUnboundedMaxFollowsBuilderMutation`，该用例在旧实现上稳定失败，修复后通过

### 4.2 执行树父指针已失去用途

**现象**

`EvalNode.parent` 只在 `RuleVisitor.visit` 中写入，Core、UI 和 Web 均没有读取方

**设计意图**

早期 `RuleVisitor` 依靠 `EvalNode.getParent()` 回溯执行栈，后来已改为保存方法局部变量 `parent` 并在 `finally` 恢复，但字段和写入遗留了下来

**修复**

删除 `EvalNode.parent` 及唯一写入点，不改变详情树子节点结构

### 4.3 `RuleVisitor` 和并行任务保留上一次执行状态

**现象**

`currentEval` 和 `currentRule` 是每次执行新建的 `ThreadLocal`，根调用和 `ForkJoinPool.commonPool()` 工作线程结束后分别保留最后的 `EvalNode` 和规则 ID

`EvalNode` 连接子树和业务结果，长生命线程会额外保留上一次执行数据；两个过期条目都会残留在线程的 `ThreadLocalMap` 中

**设计意图**

`ThreadLocal` 用于让并行分支维护独立的当前节点和规则 ID，不是用于跨次执行缓存状态

**修复**

- 根访问结束时调用 `ThreadLocal.remove()`
- 规则 ID 在节点退出时恢复上层值，根节点退出时清理
- `setCurrentEval(null)` 明确转为 `remove()`
- 并行任务在 `finally` 中清理工作线程状态

该修复只在根调用或并行任务退出时增加清理操作，没有新增堆分配

新增 `testVisitorClearsCurrentRuleAfterRootVisit`，锁定根节点退出后不再保留过期规则 ID

### 4.4 `CompositeNode` 保留已不可达的参数检查

**现象**

`CompositeNode` 构造器始终调用 `super(ruleId, null)`，`eval` 中对 `getArguments() != null` 的检查在当前代码中不可达，构造器注释仍说“带调用参数”

**设计意图**

Git 历史显示早期复合节点支持参数，后续已明确改为命名复合规则按 `ruleId` 复用并忽略外层参数

**修复**

删除不可达分支并修正构造器说明，不改变当前复合规则语义

### 4.5 `NodeBuilder` 依赖未声明的 JetBrains 注解

**现象**

`NodeBuilder.generator` 使用 `org.jetbrains.annotations.NotNull`，Core POM 没有声明该依赖，实际依赖来自 Jackson Kotlin 链路的传递依赖

**设计意图**

`generator` 在所有构造路径中仅赋值一次，不需要外部可空注解；Lombok 构造器只需保持现有 `NodeBuilder(NodeGenerator)` 签名

**修复**

删除注解和 import，将字段设为 `final`，Lombok 仍生成相同构造器

Maven 依赖分析复审后，`org.jetbrains:annotations` 的“已使用但未声明”告警已消失

### 4.6 Rhino 1.9.1 废弃的 `Script.exec` 重载

**现象**

`RhinoEngine.doEvaluate`、`JsUdf.bind` 和 `JsUdf.compileFunction` 使用已废弃的两参数 `Script.exec(Context, Scriptable)`

**设计意图**

Rhino 1.9.1 源码中，两参数默认实现只是调用 `exec(context, scope, scope)`

**修复**

三处均替换为完全等价的三参数形式，编译时的 Rhino 废弃 API 告警已消失

### 4.7 `JsUdf` 注释与实际兼容行为相反

**现象**

类注释说“不支持辅助函数、变量声明加入口函数”，`compileFunction` 却有专门的历史脚本回退编译路径，现有测试也明确覆盖辅助函数

**设计意图**

Git 提交 `344337b` 明确恢复了多语句历史 UDF 兼容，代码是正确的，注释未同步

**修复**

修正类说明，同时明确单函数表达式和历史入口脚本两种格式

### 4.8 Core 构造器使用 `Objects.requireNonNull`

**现象**

`RuleSuite(RuleEngine, NodeBuilder)` 使用两处 `Objects.requireNonNull`，与 Core 构造器的项目约束不符

**设计意图**

两个对象会存入字段并在后续执行时才解引用，因此构造时立即报错的原契约有明确意义

**修复**

保留原有 `NullPointerException` 类型、触发时机和消息，仅替换为显式边界检查

### 4.9 未使用 import

PMD 确认两处无读取方的 import：

- `DefaultRuleVisitor` 的 `TerminalNode`
- `NodeGenerator` 的 `java.util.function.Function`

两处均已删除

## 6. 经意图核对后不修改的项目

### 6.1 RuleEngine 描述模板缓存

`evalRuleDesc` 已直接从 `compiledRuleDesc` 按 `ruleId` 读取注册期快照，稳态路径不再调用 `compiledDesc.computeIfAbsent`

`compiledDesc` 只用于构造期对相同描述文本去重，不是死代码，不删除

### 6.2 没有 `apply` 的 Java UDF 对象

现有 `testPlainObjectMemberMethodIsCallable` 明确要求普通 Java 对象可以只作为成员方法容器注册，只有直接函数调用时才报告没有匹配 `apply`

因此“注册时强制存在 `apply`”会破坏已有设计，本轮明确不做

### 6.3 JavaScript UDF 闭包状态

JavaScript UDF 在 RuleEngine 构造阶段绑定一次，闭包状态属于当前 RuleEngine 实例，现有测试明确锁定该语义，不改为每次执行重建

### 6.4 命名复合规则参数

命名复合规则按 `ruleId` 编译和复用，外层调用参数按设计忽略，不引入参数化复合节点变体

### 6.5 兼容类型

`RuleParseException`、`RuleMatchException`、`RuleListener.onParse` 和解析事件枚举已在设计文档中标明为保留类型，不按当前调用数删除

### 6.6 节点表达式缓存

`AbstractRuleNode.expr` 假定树在求值期已构建完成，是经 JFR 验证的性能设计

本轮不因“构建后仍可以人为修改子集合”而取消表达式缓存，`SomeNode` 修复也不引入 O(n) 拷贝

### 6.7 复审撤回：构造期调用可重写方法

第一轮审查曾将 `NodeBuilder(List)` 调用 `build` 以及 `UdfContainer(List)` 调用 `register` 视为潜在坏味道

复审确认仓库内没有这两个类的子类，也没有实际重写场景，该判断只基于假设子类，不能证明当前代码存在缺陷

已撤回绕过公开方法的修改和对应测试，也不为假设场景新增 `final`，两个构造器保持原实现

# 模板参数化规则

> 文档状态：随当前代码维护
>
> 适用模块：`mosika-core`
>
> 更新时间：2026-08-06

## 1. Feature 定位

模板参数化规则是 Mosika 的一项核心能力升级：一条原子规则定义可以作为可复用模板，在同一棵规则树中由不同节点绑定不同参数

它解决的不是 JavaScript 函数传参问题，而是规则定义复用问题。只有阈值、等级、地域或策略参数不同的场景，不再需要复制多条几乎相同的 `RuleDefinition`

```text
升级前：
r1 = $.input > 100
r2 = $.input > 200
r3 = $.input > 300

升级后：
threshold = $.input > $args.limit
```

调用方在规则 ID DSL 的节点上绑定参数：

```text
threshold("""{"limit":100}""") || threshold("""{"limit":300}""")
```

这样保持了两个重要边界：

- 规则定义仍然只负责表达稳定业务逻辑
- 每个规则节点只负责提供本次调用的配置参数

## 2. 快速开始

定义一条模板规则：

```java
RuleDefinition threshold = new RuleDefinition(
        "threshold",
        "$.input > $args.limit",
        "输入=${$.input}，阈值=${$args.limit}");
```

装配并执行：

```java
RuleSuite suite = new RuleSuite(List.of(threshold), List.of());

NodeResult result = suite.eval(
        "threshold(\"\"\"{\"limit\":100}\"\"\")"
                + "||threshold(\"\"\"{\"limit\":20}\"\"\")",
        Map.of("input", 50));
```

第一次调用结果为 `false`，第二次调用结果为 `true`，逻辑或最终返回 `true`。两次调用会分别出现在执行详情中，动态描述也会分别得到 `limit=100` 和 `limit=20`

## 3. 三个运行时入口

原子规则和规则描述共享同一组绑定：

| 名称 | 生命周期 | 含义 |
| --- | --- | --- |
| `$` | 本次顶层执行 | 业务输入对象，即 `RuleVisitor.data` |
| `$$` | 本次顶层执行 | 共享的可变规则上下文，即 `RuleVisitor` |
| `$args` | 当前原子规则节点 | 当前节点绑定的模板参数对象 |

示例：

```javascript
$.age >= $args.minAge && $$.enabled
```

三个对象职责不同：

- `$` 是外部传入的业务数据
- `$$` 用于同一次执行中跨规则共享和回写状态
- `$args` 是规则模板本次实例化的局部配置

未传模板参数时，`$args` 绑定为空对象，不影响已有规则继续使用 `$` 和 `$$`

## 4. DSL 语法

参数化规则节点使用三引号包围参数文本：

```text
ruleId("""JSON object""")
```

例如：

```text
r001("""{"name":"jack","age":18}""")
```

参数可以跨行：

```text
r001("""{
  "name": "jack",
  "contacts": [
    {"type": "phone", "value": "123"}
  ]
}""")
```

ANTLR4 只识别三引号参数块的开始和结束，不解析 JSON 内部结构。`DefaultRuleVisitor` 取出原始文本后，由 `RuleArguments` 在 `ExprNode` 构造阶段一次性生成规范化 JSON 字符串和字段有序的 `Map<String,Object>`

这种分工避免让规则 DSL 重复实现 JSON 语法，也避免对象、数组、字符串和嵌套括号干扰外层规则组合解析。参数不是 JavaScript 源码片段，不会被拼接或替换进规则表达式

当前参数约束：

- 根值必须是 JSON 对象，不能是数组、字符串、数字或 `null`
- 空参数和不合法 JSON 在节点构建阶段直接失败
- `expr()` 会把参数规范化为紧凑 JSON，保证节点表达式可重新解析

## 5. 编译与执行链路

```text
ruleId("""{...}""")
  -> Rule.g4 / DefaultRuleVisitor
  -> ExprNode(ruleId, arguments Map)
  -> RuleVisitor.eval(ruleId, arguments)
  -> RuleEngine.evalRule(ruleId, target, context, arguments)
  -> GraalJS bindings: $ / $$ / $args / UDF
  -> EvalResult
  -> 当前 EvalNode
```

规则 JavaScript `Source` 仍按 `RuleDefinition.expression` 预编译和复用。变化只发生在每次执行创建的 GraalJS `Context` 中：当前节点参数作为 `$args` 绑定进去，因此不需要为每组参数重新编译 JavaScript

这是一种运行时绑定，但节点实例在 DSL 解析时已经确定了参数，所以同一个模板规则可以在一棵执行树中出现多次

## 6. 缓存与多次执行语义

无参数和有参数调用使用不同形式的缓存键：

| 调用形式 | 单次顶层执行中的行为 |
| --- | --- |
| `r001` | 按 `ruleId` 复用叶子评估结果，保持既有语义 |
| `r001("""{"limit":100}""")` | 按规则 ID 和规范化 JSON 字符串组成的不可变键复用叶子评估结果 |

参数完全相同时，下面两次调用只真正求值一次：

```text
r001("""{"limit":100}""")->r001("""{"limit":100}""")
```

两个调用仍分别生成执行节点，并保存各自的结果和动态描述。参数在节点解析阶段转换为递归排序对象字段的规范化 JSON 字符串，同时保留用于绑定 `$args` 的解析结果；执行阶段不再重复解析或规范化。缓存键不可变且不受对象字段顺序影响；数组元素顺序保留，顺序不同会分别求值。这样既避免只按 `ruleId` 缓存造成参数串用，也保持了相同参数结构在一次顶层执行中的结果复用语义

## 7. 执行详情和动态描述

每个 `EvalNode` 保存当前执行路径上自己的 `EvalResult`。因此同一规则的多次参数化调用不会在详情阶段重新按 `ruleId` 查找并合并结果

详情中的 `expr` 保留规范化参数：

```text
r001("""{"limit":100}""")
r001("""{"limit":300}""")
```

`RuleDefinition.desc` 使用与规则表达式相同的 `$`、`$$` 和 `$args`：

```text
输入=${$.input}，阈值=${$args.limit}
```

详情渲染时会把当前节点的同一份参数传给描述表达式，所以规则结果、调用表达式和描述保持一致

## 8. 当前边界

模板参数当前只对原子 `ExprNode` 具有执行语义

`CompositeNode` 继承了参数的语法承载能力，因此参数化复合规则可以被解析和规范化表达；但当前不会把参数隐式传给内部规则，也不支持带参数复合规则执行。这样可以先保持 AST 语法闭合，同时避免在没有明确作用域规则前引入参数继承、覆盖和透传语义

参考 Web 当前把 `$args` 作为运行时保留顶级名称，用户 UDF 不能覆盖它。参数化调用的可视化配置属于产品层编辑能力，不改变 Core 的参数绑定契约
